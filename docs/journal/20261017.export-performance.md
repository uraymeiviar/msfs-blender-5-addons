## Session 1: Profiling and Fix Plan

- **Date:** 20261017
- **Developer:** uraymeiviar
- **Agent:** Claude Code (Opus 5.5)
- **Branch:** main
- **Base Commit SHA:** 9629b43

### Problem Statement

Deploying the E2 cockpit with all LODs (`D:\fss-e2\assets\visual\cockpit\deploy_cockpit_gltf_lods.bat`) takes 15 to 20 minutes (973 s and 985 s measured), which blocks development. **Target: 5 minutes or less** for the same deploy (seven files, `_LOD00` to `_LOD06`), with identical output.

### Constraints (maintainer)

- **No multiple Blender processes** in parallel: heavier on the machine and still slow per export.
- **No threads:** the exporter is Python under one interpreter lock, `bpy` is not thread-safe, and every LOD needs its own scene state.
- **Native code later:** hot paths may move to native DLLs once the Python-level waste is removed; not part of this task unless the target cannot be reached otherwise.
- Output must stay identical: compare the glTF files before and after every change (node names and hierarchy, world matrices, attributes, indices, materials, animations).

### Measurements

- **Whole LOD deploy (973 s):** about 80 % in the glTF exporter per LOD (182 s for `_LOD00` down to 45 s for `_LOD06`), the rest reloading and preparing the scene between LODs (about 28 s per LOD).
- **One single-file cockpit export under cProfile (237 s total; tool: `tests/profile_export.py`):**

  | Where | Time | Notes |
  | :--- | ---: | :--- |
  | `io_scene_gltf2/blender/exp/nodes.py` `__gather_mesh`, own time | 171 s | 2,479 calls; the time is inside Blender API calls it makes, not in Python |
  | `fss_blender_tools/empty_bounds.py` `_on_depsgraph_update` | 25 s | 617 calls, 4.2 million `_invalidate_chain` calls; viewport drawing support, useless in a background export |
  | multi-exporter preparation (`prepare_objects_for_selection`, duplication) | 25 s | overlaps the line above (depsgraph updates during selection) |
  | FSS merge (`merge.run`) | 7 s | |
  | Mesh conversion proper (`gather_primitives`, `extract_primitives`) | 2 s | the actual geometry work is cheap |

- **Root cause of the 171 s (verified on a copy of `COCKPIT.blend`):** `msfs_gather_mesh` in `io_scene_gltf2_msfs_fss/io/exp/gltf_exporter_patches.py` (FSS-owned) fixes object-linked material slots under modifiers by writing the object's materials into the mesh data before Khronos' `__gather_mesh`, and restoring them afterwards. Writing mesh data marks the scene as changed, so `__gather_mesh`'s `bpy.context.evaluated_depsgraph_get()` re-evaluates the whole scene for every such object. 589 cockpit objects take this path; one swap plus `evaluated_depsgraph_get()` costs about 160 ms on the plain scene (more during export, where the scene also holds the duplicates). In isolation the same API calls without a swap take under 1 ms (`evaluated_depsgraph_get`, `data.validate()`, `to_mesh`).

### Proposed Fixes, in Order

1. **Material swap once, not per object** (`gltf_exporter_patches.py`, FSS-owned). Before the gather (for example in the multi-exporter's preparation, or a pre-export hook), apply the object-to-data material assignment for all affected objects in one pass, so the scene is evaluated once.
   - The multi-exporter works on duplicates made with `bpy.ops.object.duplicate(linked=False)`, which copy the mesh data; on them the assignment needs no restore (the duplicates are purged after the export). Verify that every affected duplicate has its own mesh (a mesh shared between duplicates must be assigned only if all its users agree, or copied).
   - The plain exporter (fs20, interactive exports) works on the originals: assign before the export and restore after it, both in one pass each (two evaluations instead of 2 × 589).
   - Keep `msfs_gather_mesh` behaviour for objects not covered by the pass (it must remain correct, just no longer the common path).
   - Expected saving: most of the 171 s per export.
2. **Empty Bounds handler off in background** (`fss_blender_tools/empty_bounds.py`): register `_on_depsgraph_update` only when `bpy.app.background` is false (nothing is drawn in background), or return immediately while an export runs. Expected saving: about 25 s per export.
3. **Re-measure**, then decide on the remaining overhead:
   - **Reload between LODs** (about 28 s each, 6 times): measure `open_mainfile` versus migration, `build_plan` and the multi-exporter's duplication; options are caching the plan across reloads (it is built once already) or avoiding the reload if the export can restore the scene exactly (risky; the reload guarantees a clean source).
   - **Multi-exporter preparation** (selection and duplication, about 25 s): check for further per-object depsgraph updates.
   - Only then consider native code for the remaining hot paths.

### Expected Result

With fixes 1 and 2 a single cockpit export should drop from about 237 s to roughly 40 to 60 s, and the seven-LOD deploy from about 975 s to roughly 4 to 6 minutes (later LODs are smaller, reloads stay). Fix 3 decides whether 5 minutes is reached. These are projections; the implementation session measures them.

### Implemented

- **Fix 1, `io_scene_gltf2_msfs_fss/io/exp/gltf_exporter_patches.py`:** `assign_linked_materials(objects)` assigns object-linked materials to the mesh data once, called from the FSS `pre_export_hook` in `io_scene_gltf2_msfs_fss/__init__.py` after `instancing.prepare`, for throwaway objects only (multi-exporter duplicates carrying `msfs_original_name`, or every object in a background run), so nothing is restored. A mesh shared by several objects is changed only where every user shows the same material in that slot; other objects keep the per-object `msfs_gather_mesh` path, which is unchanged. The exporter's `bl_info` version stays 8.4.1.
- **Fix 2, `fss_blender_tools/empty_bounds.py`:** the depsgraph handler is not registered in background Blender. `fss_blender_tools` 0.15.2.

## Session 3: Second Phase, 255 s to 67 s

- **Date:** 20261017
- **Developer:** uraymeiviar
- **Agent:** Claude Code (Opus 5.5)
- **Branch:** main
- **Base Commit SHA:** 990777b

### Implemented (each step profiled with `tests/profile_export.py` before and after)

1. **Operator attribute access in a hot loop** (`io_scene_gltf2_msfs_fss/io/exp/multi_export.py`, marked FSS spot in `prepare_objects_for_selection`): `self._object_layer_collections` and `self._treated_layer_collections` are read once into locals. Attribute access on an operator resolves its RNA properties every time; the loop made 110 million such accesses for the cockpit's seven LODs (140 s profiled).
2. **Name lookups** (`fss_blender_tools/merge.py` `exported()`): a set of the view layer's object names, built once per export, before the original lookup (which scans the collection; 146,666 calls).
3. **No per-object material swaps left** (`gltf_exporter_patches.assign_linked_materials`): a mesh shared by objects that disagree on a slot's material is copied for each object that needs a change, so no object takes the per-object path in `msfs_gather_mesh` any more (each such swap re-evaluated the scene twice).
4. **Merge in two phases** (`merge.py`): `merge_group` reads a group's evaluated meshes and returns a build step; `run` reads every group from one evaluated scene, then builds all of them and updates the view layer once. Before, each built group added objects and the next group's evaluation re-evaluated the whole scene (11 groups times 7 LODs).
5. **`select_object`** (`multi_export.py`, marked FSS spot): one set of the view layer's objects per selection pass instead of building a list of all objects on every call (21,693 calls).
6. **Absent parts hidden before the export** (`fss_blender_tools/lod_model.py` `begin_export`): parts absent from the LOD are hidden in the source scene, so the multi-exporter never duplicates, selects or walks them (`_LOD06` keeps about 400 of 3,099 objects). The driver reloads the source before every LOD; `cull_export` still decides on the copies.
7. **Defect found and fixed (from Session 2's fix 1):** `assign_linked_materials` was called with every object in a background run, which under the multi-exporter included the source objects; a source object given an export-created mesh copy was deleted with that mesh by the exporter's purge after the export. Harmless before step 6 (the driver reloads, the single-file deploy quits), but wrong. Now only the multi-exporter's duplicates are processed, or, without duplicates, every object of a background run (plain exporter, which has no purge).

| :--- | ---: | ---: |

MSFS addresses nodes by name, never these mesh names.
