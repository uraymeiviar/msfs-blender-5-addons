### What Moves to C++ (Step 5)

1. **Measured first:** the parts of `compose_s` on one large cockpit master, profiled. The bake's GPU or Cycles time
   is not needed for that: a script can build a master's layout as the runner does (`build_master` of a cockpit
   object) and run `bake_paged` with a `bake_tile` that fills each tile with seeded values at once, so only the
   post-processing is timed. A part under 2 % of a large master's `compose_s` stays in Python, and Session 2 says so
   with its number.
2. **`compose_block` in C++** (or the parts of it that cost): the corner fix (`np.minimum.at` against the values as
   baked), the nearest fill inside each island's rectangle, the face map (core triangles, then skirt triangles inside
   rectangles, grown `FILL` steps inside rectangles), the counts, bit-identical, multithreaded. The DLL already has
   the raster (`fss_ao_copy_raster_ids`) and the dilation (`fss_ao_copy_dilate`, with a mask) bit-identical to
   `rasterize_ids` and `dilate_ids`; `compose_block` may call them from C++ without coming back to Python.
3. **The map writer:** `MapRowWriter`'s rows compressed in C++ (zlib 1.3.2 is already in the DLL) on a thread beside
   the composition, **only if** the `.ao.map` stays byte-identical to Python's (zlib 1.3.1, level 1, one stream); the
   files are not PNGs, so decision 4 does not cover them. If the bytes differ, the Python writer stays and Session 2
   reports the measured difference and what a parallel map writer would gain, as a proposal.
4. **Left as they are:** the tiles' bake (Cycles, FSS OptiX), the bake's orchestration, the denoise and the
   curvature (C++ in the baker; Python only without FSS OptiX), libjxl's encode, the master's `.npz`.

`compose_block` stays the fallback (`FSS_AO_COPY=numpy`, the DLL missing). Threads: the bake's Threads setting
through `threads_of` (decision 5); the runner passes `SET['threads']`.

### Rules for the DLL

The rules of the Apply journal (Sessions 1, 4, 7 and 10) hold: C interface, error codes and a message buffer, no
exception across the boundary, `/MT`, no global state, a version function (interface version 5), the caller owns
every buffer, `/fp:precise` and no FMA in the add-on's own code, deterministic for any thread count, `KERNEL32.dll`
the only import. Also:

- **Byte-identical masters:** every master file a bake writes (`.ao.jxl`, `.ao.map`, `.npz`, the index entry but its
  times) equals the Python path's, for every master of the AO suite and for a cockpit master.
- **Memory:** a window's arrays, as the Python code holds; nothing in proportion to a master (decision 33).

### Built

- `native/ao_copy/fss_ao_compose.cpp` (new) and `fss_ao_copy.h`: interface version 5.
  - `fss_ao_compose_block(layout, values, values_stride, baked, baked_stride, ex0, ey0, ew, eh, x0, y0, w, h, threads,
    out_values, out_filled, out_face, out_code, out_stride, counts)`: `compose_block` of one window. The layout
    (`fss_ao_compose_layout`, every field 8 bytes) holds `FILL`, `int(CORNER_EXCESS * 65535)`, the rectangles,
    `muv[core_tris]` with `core_tris`, the skirt's UVs with `skirt_src` (none when `skirt_pos` is empty), and the
    corner pairs. In the order of the Python code: the corner rule (decision 57); `rect_window` (a later rectangle
    wins); the nearest fill (the baked pixels' indices grown `FILL` steps inside the rectangles, a source of the same
    rectangle); the face map (`tris_in_window` with margin 1 and `rasterize_ids`' sample rule with eps 1e-9, the last
    triangle winning; the skirt's faces where the core has none inside a rectangle; grown `FILL` steps inside the
    rectangles); the counts in `compose_block`'s key order. Out: the values and, when asked, the filled flags, the
    faces and the map codes, with a row stride, so `compose_band` hands in its strip's columns and nothing is copied.
  - Threads: a team of `min(threads, jobs, pixels / 16,384)` threads for the call (the caller is one of them). The
    threads take jobs of 8 rows, interleaved, and meet at a barrier between the steps. The dilation follows
    `dilate_ids`' rule by its frontier: the first step scans every pixel; the later ones visit only the neighbours of
    the pixels that grew in the step before. A pixel takes its first neighbour with an owner in `dilate_ids`' order
    ((0,1), (0,-1), (1,0), (-1,0), then the diagonals), so the owners are the same. Each job writes only its own rows,
    and nothing depends on the thread count. The buffers are a window's; nothing grows with the master (decision 33).
  - `fss_ao_map_open`, `fss_ao_map_write`, `fss_ao_map_close`, `fss_ao_map_abort`, `fss_ao_map_stats`: the `.ao.map`
    writer. It writes the header, then one zlib stream (`deflateInit2(level, Z_DEFLATED, MAX_WBITS, 8,
    Z_DEFAULT_STRATEGY)`, which is Python's `zlib.compressobj(level)`), `Z_NO_FLUSH` as the rows come and `Z_FINISH`
    at close. At 2 threads or more it compresses on one thread beside the caller (`write()` copies the rows and
    returns; it waits while 3 writes are queued); at 1 thread it compresses in `write()`. It takes rows with any
    stride (the strips come flipped, a negative stride). Too many rows, a missing folder or a write error give an error
    with a message naming the file, and the file is removed; abort removes it too.
- `build.cmd`: `fss_ao_compose.cpp` joins the second `cl` call (no `/MP`). Built under `cpucap.exe 50` with `/W4 /WX`
  and no warning: 383,488 bytes, md5 `7ef66967ac447b09938e9ca458396d72`; `dumpbin` shows `KERNEL32.dll` only and 22
  exports; the disassembly (80,895 lines) has the same 9 FMA instructions as before (the C runtime's `log10`).
- `ao_bake_copy.py`: `VERSION = 5`, `ComposeLayout`, `Layout` and `compose_layout()` (the layout's arrays made once
  per master), `compose()` (the counts as a dict in `compose_block`'s key order), `MapWriter` (`MapRowWriter`'s
  `write`, `close` and `abort`; `by`, `map_stats`), `MapError` (a `CopyError`, so an `OSError`), `MapStats`.
- `ao_bake_core.py`:
  - `compose_native()` (C++ when `ao_bake_copy.backend()` is native and the block is uint16 and bool),

  barriers, rather than a pool per step.

### What Moves to C++

1. **Measured first:** `refresh_prof.py` (Session 1, `tests/_work/ao_bake/refresh_prof/`) on the cockpit copy, two

3. **`moves_against`, batched:** all the (object, occluder) pairs of a pass in one call (`inv(Ma[0]) @ Mb[0]`, the

   gather; `evaluated_triangles`'s `foreach_get` stays (Blender's), its numpy gathers move only if measured faster.
5. **`_hash` (the surroundings key's JSON, then SHA-1):** stays in Python unless a C++ encoding is byte-identical to

### numpy's Order of Operations

Measured on Blender's numpy 2.3 with `math.fma` (`numpy_order.py`, `numpy_order2.py`): `matmul` (2-D and stacked:
`(8, 3) @ R.T`, `(k, 15, 3) @ (3, 3)`, `axes.T @ axes`, `(P, 4, 4) @ (4, 4)`) and `einsum('kmx,kxj->kmj')` sum their
products in order, `((p0 + p1) + p2) + p3`, without FMA, in every case; `einsum('kij,nj->kni')`, `'...ij,...j->...i'`
and `'kmx,kx->km'` (a contiguous axis reduced in both operands) give `(p0 + p2) + p1` in every case; `np.cross`,
`np.linalg.norm` over either axis and the sums of three are in order. The C++ follows these, and its gaps came out bit
for bit equal. `np.linalg.inv` stays numpy's (the caller passes the inverses).

### Choices Made Here (Proposals)

- Refresh computes the scene rule and the pairs' motion for every baked object before the items' loop, a few more
  than the loop uses (objects without a texture set, the copies One Instance does not bake); those results are not
  stored. `custom_occluders` is called there once per object and reused.
- The motion test's inverses are numpy's, passed to the DLL, so they stay the Python code's bit for bit.
- `mesh_hash` checks the CPU for the SHA instructions at each call (no global state); a CPU without them gets the
  plain C++ SHA-1, still faster than Blender's `hashlib` here (0.16 against 0.21 s).
- `test_unavailable` stubs Refresh for the job it starts past the polls, and `test_oriented_rule` uses the DLL's own
  boxes; `core.box_gap` went with the Python geometry (only that test called it).
- The suite's Refresh check runs only when `test_ao_bake.py` is the script run: `test_ao_bake_native.py` and
  `test_ao_bake_native_job.py` import it for its scene and failed on the check before this was added.
- `RULE_STATS` (the last pass's closest gaps and counts) is kept for the measuring scripts; nothing shows it.
- This session's edits made with a Windows Python wrote CRLF; the files were put back to LF, as they were.
