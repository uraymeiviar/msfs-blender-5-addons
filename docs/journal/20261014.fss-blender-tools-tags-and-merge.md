## Session 1: Design, Exporter Findings and First Version

- **Date:** 20261014
- **Developer:** uraymeiviar
- **Agent:** Claude Code (Opus 5.5)
- **Branch:** dev/fs24/uray
- **Base Commit SHA:** f2fa30647 (FSS repository); add-on repository `msfs-blender-5-addons` at ee77fd6

### Problem Statement

Static detail (screws, bolts, brackets) is modelled as hundreds of separate objects so it stays editable, but every object becomes a glTF node, and the cockpit pays for the node count. Merging them in the `.blend` makes them hard to edit. Functional grouping (clickspots, screens, colliders, light meshes, decals, references) is held in Blender collections, which leaves no room to use collections for anything else.

### Maintainer Decisions

1. **Tags, not roles.** Tags are generic names the artist chooses; nothing is inferred and nothing is MSFS-specific. They are stored as the plain custom property `fss_tags` (semicolon-separated), readable and editable in vanilla Blender. An object can carry several tags.
2. **Tags are shown in the sidebar**, following the existing FSS Tools panels; no viewport overlay.
3. **Merge groups are marked by name:** an EMPTY named `MERGE_<name>`, so the grouping is visible in the Outliner and adding an object is just parenting it. The merged mesh is named `<name>`; the prefix never reaches the glTF.
4. **Nested groups merge deepest first,** then walking up. A node that cannot be merged is skipped with its subtree and the rest of the group still merges, so an inner group survives as its own mesh when the group above it cannot take it.
5. **Different materials merge, with a warning,** because merging different materials may be a mistake.
6. **The merge is implemented in fss-blender-tools,** plugged into the glTF exporter's hook, not in the exporter add-on.
7. **The merge is an export feature only:** a mesh must be explicitly under a `MERGE_` EMPTY; the MSFS model XML is not consulted.

### Exporter Findings

- The glTF exporter instantiates `glTF2ExportUserExtension` from every enabled add-on and calls `pre_export_hook` before it collects the objects (`io_scene_gltf2/__init__.py`), so a hook can change what is exported without any exporter change.
- The MSFS 2024 multi-exporter duplicates the objects, exports the selection, and after each preset purges every data block created during the export (`purge_new_data`). The hook therefore edits throwaway copies. Duplicates carry `msfs_original_name`, which the exporter's node hook writes as the glTF node name; export copies of materials carry `msfs_original_data`, the artist's material.
- `post_export_hook` is not called when the export raises, so the merge must not depend on it for clean-up. It does not: it only edits throwaway objects.
- The fs20 deploy calls the plain glTF exporter on the original objects, but in a background Blender that quits without saving.

### Solution Intent & Approach

- **`fss_blender_tools/tags.py`:** add or remove tags on the selection, a list of the file's tags with counts, select by tag (Shift extends), rename and delete a tag everywhere, the active object's tags, and Tag from Collection (tags every object of a collection with its name, for moving off functional collections).
- **`fss_blender_tools/merge.py`:**
  - Runs in `pre_export_hook` when the exported objects are throwaway: multi-exporter duplicates, or any background run. An interactive plain export is left unmerged with a warning.
  - Groups are processed deepest first, and each group is collected just before it is merged, so a merged inner group is an ordinary member of the outer one.
  - Skipped nodes: animated (action or NLA track), skinned (armature, armature modifier, bone parent), shape keys, object types other than mesh-like and empty, and objects with a tag from the panel's "Don't Merge Tags" list. A skipped node keeps its subtree unmerged.
  - Members' evaluated meshes (modifiers applied) are joined in the `MERGE_` EMPTY's space with numpy: positions, faces, material slots (mapped to the original materials), UV maps by name, the active colour attribute, and corner normals written as custom normals.
  - Opaque and transparent parts (MSFS alpha mode Blend, or Blender's Blended render method) never share a mesh: transparent parts become `<name>_TRANSPARENT`, with a warning.
  - The merged mesh takes the EMPTY's world matrix and parent. Nodes that stay because a skipped node lies below them are replaced by empties with the same world matrix, and children keep their parent-inverse matrices, so skipped nodes keep exact transforms and their animation.
  - Warnings: more than one material (with the users of each), opaque and transparent parts, more than two UV map names, and a merged name equal to a node that stays in the group.
- **Panel "Merge Groups":** Merge on Export toggle, Don't Merge Tags, New Merge Group (creates `MERGE_<name>` and parents the selection to it), Preview Merge (prints the plan without changing anything).

### Verified Behavior

Synthetic scene exported through both deploy paths (multi-exporter as fs24, plain glTF exporter in background as fs20), output in a scratch folder:

- A nested `MERGE_INNER` merged first and then into the outer `MERGE_PANEL`; no `INNER` or `MERGE_` node remains.
- The merged `PANEL` has the same vertex count (168), triangle count (84) and world bounds as the original panel, screws and bolts exported without the merge.
- The animated button and its cap, and the tagged clickspot, have world positions identical to the unmerged export, and the button's animation is exported.
- The transparent decal was exported as `PANEL_TRANSPARENT`; the warnings for three materials, opaque plus transparent parts, and the `PANEL` name clash were printed and written to the exporter log.
- The original objects in the `.blend` were not changed.

Production file: a copy of the E2 `COCKPIT.blend` with `EMPTY_PEDESTAL_PANELS` wrapped in `MERGE_PEDESTAL_PANELS`, exported through the multi-exporter into a scratch folder and compared with the same copy exported without the merge:

| | Without merge | With merge |
| :--- | :--- | :--- |
| Nodes | 3,663 | 3,559 (106 removed, `PEDESTAL_PANELS` and `PEDESTAL_PANELS_TRANSPARENT` added) |
| Mesh primitives | 2,562 | 2,464 |
| Triangles | 1,293,670 | 1,293,670 |
| Animations | 510 | 510, identical channel sets |
| Largest world-matrix difference over the 3,557 common nodes | | 6e-6 |

The 261 animated buttons and knobs of the pedestal stayed separate. Because this file has no tags yet, the group also took the MCDU and ACP screens and eight `InvisibleCollider` clickspots; the multiple-materials warning listed them. In production such objects get a tag that is listed in Don't Merge Tags.

A first version crashed Blender (access violation on the next depsgraph update): material slots were read from the evaluated object, which returns evaluated copies, and assigning those to a real mesh is invalid. The merge now maps each slot to the original material.

### Affected Files / Key Changes

- `msfs-blender-5-addons/fss_blender_tools/tags.py` (new), `merge.py` (new), `__init__.py` (registers both, exposes `glTF2ExportUserExtension`, version 0.3.0).
- `codes/wasm/doc/journal/20261014.fss-blender-tools-tags-and-merge.md` (this journal).
- `tools/blender/5.2/scripts/addons_core/fss_blender_tools/` (new: the add-on at `msfs-blender-5-addons` commit cff489a), `tools/blender/5.2/scripts/startup/fss_enable_addons.py` (enables it at every start), `tools/blender/FSS-ADDONS-VERSION.txt` (records the commit).

### Scope & Expected Behavior

- Deploys merge every visible `MERGE_` group; scenes without `MERGE_` EMPTYs export exactly as before.
- Not covered: an animated `MERGE_` EMPTY (left unmerged with a warning), merging in an interactive plain glTF export, and export limited to the active collection.

## Session 2: @MERGE_ Marker, Any Root Type, Nested Groups Kept Separate

- **Date:** 20261014
- **Developer:** uraymeiviar
- **Agent:** Claude Code (Opus 5.5)
- **Branch:** dev/fs24/uray
- **Base Commit SHA:** f2fa30647 (FSS repository); add-on repository `msfs-blender-5-addons` at cff489a

### Trigger / Problem Statement

In the production pedestal the natural group root is a mesh (`PEDESTAL_SHELL` with its sub-panels), not an empty, and flattening every nested group into its parent removes the option to keep a hierarchy of merged meshes. A plain `MERGE_` prefix could also clash with a real node name.

### Maintainer Decisions

1. **The marker is `@MERGE_`.** `@` has no meaning in Blender, glTF, the model XML or `.cfg` files; `#` was rejected because it is the macro delimiter in model behavior templates.
2. **Any node can be a group root.** A mesh root merges its own geometry together with its subtree; the result takes the root's name without the marker and the root's place.
3. **A nested `@MERGE_` node is not absorbed.** The outer walk stops at it; it merges its own subtree and stays a child node of the merged mesh around it, so merged meshes can form a hierarchy.

### Changes Made

- `merge.py`: marker `@MERGE_`; roots of any type (a mesh root is the first member); groups processed outermost first, with a nested root as a stop node; a root that cannot merge (animated, skinned, shape keys, a "don't merge" tag) leaves its group unmerged with a warning.
- `merge.py`: a `gather_node_hook` strips the marker from every glTF node name, so even an unmerged root exports as `<name>`. It runs after the MSFS exporter's node hook, which writes `msfs_original_name`, because the exporter is enabled before fss-blender-tools.
- `name_check.py`: the `@MERGE_` marker is allowed; the naming rules apply to the rest of the name.
- Version 0.4.0, add-on commits 1aa9cfd and 4b71950.

### Verification

- Synthetic scene, both deploy paths: `@MERGE_SHELL` (a mesh root with two levels of children) became one mesh `SHELL`; `@MERGE_INNER` inside `@MERGE_PANEL` became its own mesh `INNER`, a child of `PANEL`; the animated `@MERGE_ANIM` stayed unmerged and exported as `ANIM`. No glTF node name contains `@`.
- Copy of the E2 `COCKPIT.blend` with `EMPTY_PEDESTAL_PANELS` under `@MERGE_PEDESTAL_PANELS`, compared with the unmerged export: the same figures as Session 1 (3,559 against 3,663 nodes, 2,464 against 2,562 primitives, 1,293,670 triangles both, 510 identical animations, world matrices within 6e-6), and no node name with `@`.
- A first test run used the 0.3.0 copy in the portable Blender's `addons_core`, which takes precedence over a user scripts folder; the add-on there now carries the new code, so later tests load it.

### Known Issues

- Animation names are not changed. An animated `@MERGE_` root whose action is named after it (for example `@MERGE_ANIMAction`) exports that name with the marker; the model XML refers to animations by name, so they are left as authored. Name such actions without the marker.

### Affected Files

- `tools/blender/5.2/scripts/addons_core/fss_blender_tools/` (add-on 0.4.0 at commit 4b71950; replaced by 0.5.0 in Session 3).
- `codes/wasm/doc/journal/20261014.fss-blender-tools-tags-and-merge.md` (this session).

### Scope & Expected Behavior

Deploys merge every visible `@MERGE_` node with its subtree; nested `@MERGE_` nodes become child meshes; no exported node name carries the marker. Scenes without `@MERGE_` nodes export as before.

## Session 3: @NOMERGE_ Nodes and the Merge Report on the Console

- **Date:** 20261015
- **Developer:** uraymeiviar
- **Agent:** Claude Code (Opus 5.5)
- **Branch:** dev/fs24/uray
- **Base Commit SHA:** f2fa30647 (FSS repository); add-on repository `msfs-blender-5-addons` at 4b71950

### Trigger / Problem Statement

During a deploy, nothing on the console showed whether a `@MERGE_` group was merged: the merge report went to stdout, which `deploy-gltf.bat` sends to `export.log.txt`. And a group needed a way to keep a node inside it as a separate child without tagging it.

### Maintainer Decisions

- **`@NOMERGE_<name>`** marks a node inside a `@MERGE_` group that is not merged: it and its subtree stay child nodes of the merged mesh, exported as `<name>`.
- **The merge report is shown on the console during deploys.**

### Changes Made

- `merge.py`: `@NOMERGE_` is a stop node like an animated node; both markers are stripped from glTF node names and mesh names (mesh data is often named after its object).
- `merge.py`: in background runs, each group's summary line and every warning are also printed to stderr, which the deploy `.bat` leaves on the console; the per-node "kept separate" lines stay in the log only. Interactive Blender prints them once.
- `name_check.py`: accepts both markers.
- Version 0.5.0, add-on commit ff9382f.

### Verification

Synthetic scene with `@NOMERGE_BRACKET` (a mesh with a child) inside `@MERGE_PANEL`, exported with stdout redirected to a log as the deploy does: `BRACKET` and its child exported unmerged under `PANEL`; the console showed the four group summaries and the warnings; no glTF node or mesh name carries a marker (the only remaining `@` is the action name of the animated test root, see Session 2). A first run reported one error-like line that could not be reproduced in three further runs.

### Affected Files

- `tools/blender/5.2/scripts/addons_core/fss_blender_tools/` (add-on 0.5.0 at commit ff9382f; replaced by 0.6.0 in Session 4).
- `codes/wasm/doc/journal/20261014.fss-blender-tools-tags-and-merge.md` (this session).

### Scope & Expected Behavior

Deploys print one line per merge group and every merge warning on the console; `@NOMERGE_` nodes stay separate inside a group.

## Session 4: Merge Group Tree in the Sidebar

- **Date:** 20261015
- **Developer:** uraymeiviar
- **Agent:** Claude Code (Opus 5.5)
- **Branch:** dev/fs24/uray
- **Base Commit SHA:** f2fa30647 (FSS repository); add-on repository `msfs-blender-5-addons` at ff9382f

### Trigger / Problem Statement

The Merge Groups panel gave no overview: what each `@MERGE_` node will merge was only visible in the console or after an export.

### Changes Made

- `merge.py`: Refresh lists every visible `@MERGE_` group, indented by nesting, with the objects and materials it merges and the number of nodes kept separate. Rows are flagged when a group merges several materials or transparent parts, or cannot merge at all. The selected row shows the material names, why nodes stay separate (counted by reason), the UV map names, and selects the group root. Print Details keeps the full console listing.
- The tree is computed on Refresh, not on every redraw: Blender redraws the sidebar continuously, and a refresh takes about 140 ms on the E2 cockpit.
- Version 0.6.0, add-on commit 92f0721.

### Verification

Background Blender: the synthetic scene listed `INNER` under `PANEL`, the reasons for its four separate nodes (`@MERGE_`, `@NOMERGE_`, tag, animated), and the animated root as not merged. A copy of the E2 cockpit with `@MERGE_AUDIO_L` nested inside `@MERGE_PEDESTAL` refreshed in 141 ms with the expected nesting. The panel drawing itself was not checked in an interactive Blender.

### Affected Files

- `tools/blender/5.2/scripts/addons_core/fss_blender_tools/` (add-on 0.6.0 at commit 92f0721; replaced by 0.7.0 in Session 5).
- `codes/wasm/doc/journal/20261014.fss-blender-tools-tags-and-merge.md` (this session).

### Scope & Expected Behavior

Refresh shows the merge groups as a tree; the export behaviour is unchanged.

## Session 5: Bone-Parented Groups

- **Date:** 20261015
- **Developer:** uraymeiviar
- **Agent:** Claude Code (Opus 5.5)
- **Branch:** dev/fs24/uray
- **Base Commit SHA:** f2fa30647 (FSS repository); add-on repository `msfs-blender-5-addons` at 92f0721

### Trigger / Problem Statement

In the E2 cockpit, `WINDOW_L` follows bone `test1_L` of `ARMATURE_WINDOWS`. After it was grouped under `@MERGE_WINDOW_LT`, Blender reported "Failed to add relation Bone Parent, could not find BONE 'test1_L'" on `@MERGE_WINDOW_LT`. Attaching the `@MERGE_` empty to the bone instead left the group "not merged: skinned".

### Root Cause

- New Merge Group set the parts' parent to the new empty without resetting their parent type, so `WINDOW_L` kept `parent_bone = test1_L` on an empty that has no bones, and stopped following the bone. Blender's own Ctrl+P resets it.
- The merge treated any bone parent as skinning. A root that follows a bone rigidly is not skinned; only its parts must move together, which a merged mesh does.

### Changes Made

- `merge.py`: a `@MERGE_` root that follows a bone merges; the merged mesh keeps the root's parent, parent type and bone. A member that follows a bone of its own stays separate, reported as "bone-parented". Armatures and objects with an armature modifier remain "skinned".
- New Merge Group: all selected objects must share one parent and parent bone; the new empty takes that parent (on a bone, at the bone's pose matrix) and the parts become object children of it, keeping their world transforms.
- Version 0.7.0, add-on commit 325ee90.

### Verification

Synthetic armature with an animated bone and two parts parented to it, grouped with New Merge Group and exported through the multi-exporter: no relation errors, the parts kept their world positions after grouping, the merged `WINDOW_LT` is a child of the `test1_L` joint with the same vertices, triangles and world bounds as the unmerged parts, and the bone animation is exported.

### Affected Files

- `tools/blender/5.2/scripts/addons_core/fss_blender_tools/` (add-on 0.7.0 at commit 325ee90; replaced by 0.8.0 in Session 6).
- `codes/wasm/doc/journal/20261014.fss-blender-tools-tags-and-merge.md` (this session).

### Scope & Expected Behavior

Groups attached to a bone merge and keep following the bone. Objects already broken by the earlier New Merge Group (a parent bone on an empty parent) must be re-parented by hand.

## Session 6: Fix Broken Bone Parents

- **Date:** 20261015
- **Developer:** uraymeiviar
- **Agent:** Claude Code (Opus 5.5)
- **Branch:** dev/fs24/uray
- **Base Commit SHA:** f2fa30647 (FSS repository); add-on repository `msfs-blender-5-addons` at 325ee90

### Trigger / Problem Statement

After `@MERGE_WINDOW_LT` was attached to bone `test1_L`, the deploy still reported "Failed to add relation Bone Parent". The saved file showed `WINDOW_L` with parent `@MERGE_WINDOW_LT` (an empty), parent bone `test1_L` and an invalid parent type: Bone is not a valid type when the parent is not an armature, so the Relations panel showed the field blank and could not reset it. ### Verification

The broken state was rebuilt as the old New Merge Group left it (bone-parented part moved under a bone-parented empty with its parent bone kept): the button fixed it, the part moved by 0.0, and no relation error appeared after the fix. On the production file the maintainer fixed `WINDOW_L` with the equivalent Python, and the deploy no longer reports the error.

### Affected Files

- `tools/blender/5.2/scripts/addons_core/fss_blender_tools/` (add-on 0.8.0 at commit 0aa7f72, new `checks.py`; replaced by 0.8.1 in Session 7).

## Session 7: Transparent Part of a Bone-Parented Group

- **Date:** 20261015
- **Developer:** uraymeiviar
- **Agent:** Claude Code (Opus 5.5)
- **Branch:** dev/fs24/uray
- **Base Commit SHA:** 6950aafda (FSS repository); add-on repository `msfs-blender-5-addons` at 0aa7f72

### Trigger / Problem Statement

The deploy of the E2 cockpit reported "Failed to add relation Bone Parent, could not find BONE 'test1_R'" on `WINDOW_RT`, traced to `WINDOW_RT_TRANSPARENT`. The `.blend` was fine: `@MERGE_WINDOW_RT` (attached to bone `test1_R`) contains the decal `DECAL_WINDOW_R`, so the merge split off the transparent mesh `WINDOW_RT_TRANSPARENT`.

### Root Cause

The transparent mesh first copied the root's parent including its parent bone, and was then made a child of the main merged mesh without resetting its parent type: the same defect New Merge Group had (Session 5), in the merge itself. Only groups that are bone-parented and contain transparent parts are affected.

### Changes Made

- `merge.py`: the `_TRANSPARENT` mesh is a plain object child of the main merged mesh. Version 0.8.1, add-on commit e407c6c.

### Verification

The synthetic bone test with a transparent decal added reproduced the error with the previous code and exported without it with the fix; `WINDOW_LT_TRANSPARENT` is a child of `WINDOW_LT` under the `test1_L` joint, with the same geometry bounds as the unmerged parts and the bone animation exported. One run in between, most likely still on the previous code, did not report the error, so the error does not appear on every depsgraph build.

### Notes from Production Use

- A `@MERGE_` group can take objects the model XML refers to: `@MERGE_SIDECONSOLE_PILOT` merged `EFB_L_SCREEN`, so its brightness component found no material. The multiple-materials warning listed it but is easy to miss. Prevention options for later: treat screen materials (bound in `panel.cfg`) as stop nodes with their own warning, or flag merged nodes the XML refers to through the project-tree contract. Workaround: `@NOMERGE_` or a "don't merge" tag.

### Affected Files

- `tools/blender/5.2/scripts/addons_core/fss_blender_tools/` (add-on 0.8.1), `tools/blender/FSS-ADDONS-VERSION.txt` (commit e407c6c).
- `codes/wasm/doc/journal/20261014.fss-blender-tools-tags-and-merge.md` (this session).

### Scope & Expected Behavior

Bone-parented groups with transparent parts export without relation errors, and their transparent mesh moves with the group.
