# Native Mesh Library (C++ DLL)

A C++ library, built as a DLL with a C interface, for mesh processing (mesh reduction first): a mesh with all its
attributes and optimisation parameters in, a new mesh out. An independent Blender add-on is only its UI (feeds a mesh,
shows the result); Glider (`F:\glider`) and other native real-time projects use the same DLL.

## Session 1: Feasibility Concept

### Why not read and write `.blend` directly

- A `.blend` is a memory dump of Blender's structs, described by its own schema block (SDNA). Reading the blocks is
  easy; reading their meaning means reimplementing Blender's versioning code, and the mesh layout changed through 3.x,
  4.x and 5.x (generic attribute layers). The 5.0 file header changed again.
- Writing is harder: pointers are old memory addresses, every per-point, per-edge, per-face and per-corner layer must
  stay consistent, and new objects need valid ID blocks, names, user counts and collection links. A mistake can load
  and corrupt the file on the next save.
- The file stores modifiers and geometry nodes as settings, not the evaluated mesh; only Blender can evaluate them.
- No maintained C++ library reads current `.blend` files (Assimp's importer is old and read-only; Bullet's `bParse`
  reads blocks only), and none writes them.

### Why not glTF as the only input

Blender's glTF export loses, before the library sees the mesh: n-gons (triangulated), explicit edges, seam,
sharp-edge and crease flags, welded topology (vertices split at every UV or normal discontinuity), vertex groups that
are not skin weights, project marks unless carried in `extras`, and modifiers (applied or dropped). Importing back
creates new objects instead of updating the originals.

- **Pipeline tools** whose result is a final asset (LODs for export) can work on glTF alone.
- **Authoring tools** whose result goes back into the `.blend` (seams, marks) need the Blender data, because their
  input is exactly what glTF does not carry.

glTF is therefore an adapter, not the library's mesh model.

### Decisions

1. No direct `.blend` reading or writing; Blender stays the only reader and writer of `.blend` files.
2. The library is a C++ DLL with exported C functions; an independent Blender add-on (not part of
   `fss_blender_tools` or the exporter) loads it with `ctypes` and passes mesh data as flat arrays (`foreach_get` /
   `foreach_set` into numpy arrays).
3. Algorithms may wrap third-party libraries and add project improvements.
4. The library is developed in this repository; Glider uses the DLL later.
5. Glider both consumes results made offline and generates them itself (at load time or at runtime).
6. Mesh reduction is the first tool. Auto-seam stays in Python: its limits are already known from
   `20261019.automated-uv-unwrap.md`, while mesh reduction also serves the engine.
7. The library is implementation-agnostic: a mesh with all attributes and optimisation parameters in, a new mesh out.
   It is not part of the LOD export, though the LOD export may use it later.
8. Goals: fast, lightweight, multithreaded, GPU where it pays, and reduction quality up to current research. C++ is
   chosen for native real-time projects, not for Blender.
9. GPU acceleration and multithreading inside one mesh are set aside (GPU may need a different method). Parallelism
   comes from processing several meshes at once, so calls must be independent of each other.
10. The test and benchmark harness runs without Blender, so it never interferes with the add-ons and the exporter under
    active development.
11. Input is glTF and a common format such as FBX; later also meshes passed by C calls from the Blender add-on. Output
    is glTF; later also results returned by C calls. Results are inspected in Glider's glTF viewer.
12. Samples come from public mesh data, preferably assets that already have authored LODs, and results are benchmarked
    against other tools.
13. The glTF viewer is the Glider build in `H:\git-repos\gltf-viewer`; Glider also renders results to image files for
    image-based comparison.
14. The core interface of the DLL is format-agnostic: a mesh in memory in, a mesh in memory out. This is the core
    function and a must. Invokers are a separate `.exe` or Python calling the exported functions. Loading glTF / FBX
    in the DLL may be offered as well, as a convenience beside the core interface.
15. Cluster hierarchies (continuous LOD, Nanite-style) are deferred: they are mostly rendering-engine work (partitioning,
    per-cluster selection and culling). The effort goes into mesh optimisation, with reduced meshes as output.
16. Both reduction and GPU optimisation (vertex cache, overdraw, vertex fetch, quantisation) are in scope, with the
    focus on reduction. Optimisation is independent of reduction: a separate step that can always run after it.
17. The objective is shape retention, not only fewer vertices. Seams, marked sharp edges, vertex colours and other
    attributes are inputs that guide where the reducer may and may not reduce.
18. The core interface uses indexed triangles with split vertices (the GPU, glTF and meshoptimizer layout). The
    maintainer left this choice to the agent: inputs from glTF and FBX and outputs to engines need no conversion,
    vertex counts match what the GPU draws, and the reduced result is triangles in any case. The library welds
    positions internally to see the connected surface; explicit guidance (Proposed architecture, guidance channels)
    carries what split vertices cannot express.
19. The guidance channels (Proposed architecture) are confirmed, and the set is open: the more information a caller
    gives, the better the reducer can decide. New kinds of guidance are added as they prove useful in the benchmarks.
20. The library is middleware, not a one-click optimisation tool. It exposes many adjustable parameters so each caller
    can express what it expects for its own use case, and the reducer uses that guidance.
21. CMake is the master build description, for the cross-platform objective. On Windows the daily build uses the
    Visual Studio projects that CMake generates.
22. The generated Visual Studio projects are not committed: CMake writes absolute paths into them (source files,
    include folders, and the rule that re-runs `cmake.exe` when `CMakeLists.txt` changes). They live in a git-ignored
    build folder; project settings live in `CMakeLists.txt`.
23. The library is named **libPolygone**; a later UI tool is the **Polygone** app. "Polygone" is the intended
    spelling, not a typo.

### Proposed architecture

```text
 Hosts           Blender add-on, UI only (ctypes)  Glider and other native projects
                            |                              |
 C interface     exported C functions: flat arrays in, flat arrays out
                            |
 Algorithms      seams . LOD . unwrap . attribute transfer
                            |   (each wraps third-party code + project logic)
 Core model      polygon mesh . attribute channels . adjacency . weld/split
 Third-party     candidates: meshoptimizer, xatlas (MIT)
```

- **Core model:** corner-based polygon mesh, close to Blender's: positions per point, faces as offsets into a corner
  array, each corner naming a point, n-gons allowed, edges explicit when the host has them, generic named attribute
  channels with a domain (point, edge, face, corner) and a type. A triangle host (glTF, engine buffers) welds into
  this on input and splits again on output.
- **Inputs are views** (pointer, count, stride, type), so a host hands over its own buffers without copying.
- **Guidance channels** (decision 17), all optional:
  - attribute streams, each with a weight for how strongly the reducer protects it (UVs, normals, colours, any
    other);
  - feature edges: vertex pairs with a kind (seam, sharp, crease, custom) and a weight; a feature edge may still
    collapse along itself but resists leaving its line, and an infinite weight locks it;
  - per-vertex importance (for example painted by the artist), scaling the error at that vertex;
  - per-vertex locks;
  - per-triangle group (material or glTF primitive); group borders count as feature edges with their own weight.
- **Output:** the reduced streams, for each output vertex the input vertex it came from (so a caller can carry over
  data it never passed in), and the absolute error reached.
- **Runtime rules from the start** (decision 5): no exceptions, no global state, memory allocated by the caller or
  through caller-supplied callbacks, threading optional and owned by the caller, deterministic results.
- **Ownership across the boundary:** memory never changes owner. The caller asks for the result sizes, allocates the
  output arrays and passes them in; anything the DLL allocates it frees through its own exported function.
- **Runtime library:** the DLL does not depend on a C++ runtime DLL that Blender or Glider may not ship.
- **Third-party code with improvements**, in order of preference: constraints built before the call (locked vertices
  on seams, marks and material borders; attribute weights), checks and repairs after it, and replacing the library for
  one algorithm when the project's version measures better. Third-party types never appear in the C interface.
- **Coordinate axes:** Blender is +Z up, Glider and glTF are +Y up. The library is axis-neutral where it can be; where
  an algorithm needs an up axis it is a parameter.

### Proposed first step

An identity round trip: read a mesh in Blender, pass it through the DLL with no algorithm, write it back, and check
that UVs, normals, vertex groups and seams are unchanged. It proves the core model, the C interface and the `ctypes`
bridge before any algorithm exists.

### Open

- Proposed core properties (not decided): vertex locks kept exactly, absolute error reported per call, simplifying a
  subset of a mesh, deterministic results. They also keep cluster hierarchies possible later.
- Quality metrics (geometric error and silhouette for LOD; UV stretch, chart count and seam length for seams).
- Folder layout, and how the DLL reaches the Blender add-on (`deploy.ps1` copies committed files only).
