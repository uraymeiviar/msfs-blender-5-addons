# Apply's Copy in C++

Apply (AO Bake panel, `fss_blender_tools`) copies each object's master into the texture set's file. This journal
moves the copy's per-pixel work from numpy into a multithreaded C++ DLL. The bake, the masters and Apply's results
stay as they are; the design of Apply is in the auto-bake journal
([20261112.auto-bake-ao-curvature.md](20261112.auto-bake-ao-curvature.md), Sessions 17, 23, 35, 36).

### Maintainer Decisions

- **Decision 1: the copy in C++, multithreaded** (maintainer, 20261114). Apply's per-pixel work runs in a DLL loaded
  with ctypes, as the JPEG XL and OIDN libraries are. The numpy copy stays as the reference and as the fallback when
  the DLL cannot be loaded. A GPU version was considered and set aside: masters exceed a GPU texture's 16,384 px
  (SEAT_OBS is 16,638 px wide), the surface check, padding and soften would be rewritten as shaders, results could
  differ from the CPU's in the last bit, and the GPU is busy with Cycles bakes and an inference VM.
- **Decision 2: the source lives in this repository** (maintainer, 20261114): `native/ao_copy/`, the built DLL
  committed in `fss_blender_tools/lib/ao_copy/windows-x64/` like the JPEG XL DLLs. It follows libPolygone's runtime
  rules (C interface, memory owned by the caller, no exceptions across the boundary, no C++ runtime DLL,
  deterministic), but it is not part of libPolygone.

#### What Moves to C++

Per band, Python keeps what it does today up to the per-pixel loops: `copy_context`, the band raster at one sample
per pixel (`owner_c`, `count_c`), `dilate_ids`, the hinged neighbour triangles of padding pixels, `soften_context`,
`_soften` (it calls `read`; keep a Python `read` for it), the band bookkeeping and the PNG. The DLL does:

1. **Inside pixels:** for every pixel with an owner and its level L (`kt` of its owner): the L x L sub-sample owners
   exactly as `raster_window(uvpx, ..., L, ...)` gives them (every triangle tested in index order, the last one whose
   barycentrics are all at least -1e-9 wins, with `rasterize_ids`' integer bounding-box test before the barycentric
   test), the `outside_mode='tri'` rule, `barycentric_many`, `read` (the clamp into the island's rectangle or
   `rect_id`, `filled`, the barycentric clamp, `_surface_bilinear` with the face map, `tri_normal` and `surface_cos`,
   the plain `bilinear` fallback), the weighted mean, and the centre value when no sub-sample counts. Also the count
   of clamped points (`info['clamped_inside_points']`).
2. **Padding pixels:** given each padding pixel's source triangle and its hinged UV triangle, the L x L points
   (barycentrics clamped and renormalized), `read`, and the mean.

The master is read from the scratch page files `open_master` writes (tiles of `PAGE_TILE` px; uint16 AO, int32 map
codes), memory-mapped, or from whole arrays (`load_master`, tests). The DLL gets pointers, sizes and the tile layout;
it allocates nothing the caller has to free.

#### Rules for the DLL

- **Results byte-identical to the numpy copy.** Float64 throughout, the same formulas in the same operation order;
  `/fp:precise`, no FMA contraction, no fast-math. Where numpy reduces, reproduce its order: `np.add.reduce` over a
  contiguous axis uses pairwise summation (eight partial sums in blocks of 128 elements), so a mean of 64 sub-samples
  is not a plain loop; `np.einsum('nk,nkd->nd')` and the 4-tap sums must be checked the same way. Build a small
  harness that compares each C++ function with its numpy counterpart on random inputs, bit for bit, before
  wiring it into Apply.
- **Deterministic for any thread count:** each pixel's result depends only on its inputs; threads split pixels, never
  a pixel's sum.
- **Threads:** the bake's Threads setting (`scene.fss_ao_bake.threads`), at most 12.
- **C interface:** plain C functions and structs, error codes, no exceptions across the boundary, static C runtime
  (`/MT`), a version function. No global state.
- **Fallback:** when the DLL cannot be loaded, or `FSS_AO_COPY=numpy` is set, Apply runs the numpy copy. Apply's
  report says which copy ran.

  `np.add.reduce` of a contiguous axis is 0 plus the pairwise sum (eight partial sums up to 128 values, halves above);

## Session 4: Hand-Off, Opening the Master in C++

- **Date:** 20261115
- **Developer:** uraymeiviar, Claude Opus 5.5 (the hand-off; executed by a sub-agent, which appends Session 5)
- **Base Commit SHA:** ad84181, plus the uncommitted working tree of `fss_blender_tools` 0.90.3

### Why

`open_master` is more than half of the foam's Apply (10.3 of 18.5 s; 9.1 of 15.4 s for the curvature), and on a slow
disk it is nearly all of it. It decodes the master's JPEG XL through a Python callback with one decoder thread (the
callback is the limit, auto-bake Session 27), inflates the `.ao.map` in Python, and writes both into tiled scratch
page files with numpy (`_TiledSink`, `_TiledWriter`), which go to the disk.

### What Moves to C++

A new function in `fss_ao_copy.dll` (interface version 2) fills the two page files of `open_master`:

1. **The image:** the `.ao.jxl` (or `.curv.jxl`, `.ao.raw.jxl`: every `kind` `open_master` takes) decoded by libjxl
   with its thread runner (the bake's Threads setting, at most 12) and a multithreaded image-out callback
   (`JxlDecoderSetMultithreadedImageOutCallback`) that writes each piece straight into its tiles. libjxl is the
   add-on's own `lib/jxl/windows-x64` DLLs, loaded by the DLL from the folder Python passes (`LoadLibraryExW` with the
   full path; Python has already loaded them, `ao_bake_jxl.load()`), declared by hand as `ao_bake_jxl.py` declares them
   (libjxl 0.12). The file is read in pieces as `decode_rows` reads it, never whole.
2. **The map:** the `.ao.map` (its header, then one zlib stream of int32 rows from the top) inflated and written into
   its tiles. zlib from source: copy `F:\glider\libs\zlib` (zlib 1.3.2, the maintainer's checked-out copy; nothing is
   downloaded) into `native/third_party/zlib/` with its LICENSE, compiled into the DLL (static, no zlib DLL). The image
   and the map may run at the same time (two jobs of the thread budget).
3. **The page files:** the same files, names, sizes, tile layout and byte contents as today (`PAGE_TILE` 256, tile
   (ty, tx) at index ty * ntx + tx, its pixels row-major, array row 0 at the bottom, zeros outside the image), so
   `PagedArray`, the C++ copy's tiled read and everything after the opening stay unchanged. The DLL creates each file
   at the path Python gives with `FILE_ATTRIBUTE_TEMPORARY` (Windows keeps it in its cache while memory allows instead
   of writing it out; decision 33 of the auto-bake journal still holds: no memory in proportion to the master),
   sizes it, fills it through a mapping, unmaps and closes it before returning. On an error it removes what it
   created. It allocates nothing the caller has to free.

`open_master` calls it for a `.jxl` image with a `.ao.map` when the DLL is loaded; otherwise (the DLL missing, a PNG
master, schema 1, `FSS_AO_COPY=numpy` or the new `FSS_AO_OPEN=python`) it runs the Python code, unchanged. The

### Rules for the DLL

The rules of Session 1 hold (C interface, error codes, no exception across the boundary, `/MT`, no global state, a
version function, deterministic for any thread count, the caller owns every buffer). Also:

- **Byte-identical page files:** for every master, the two files the DLL writes equal the files the Python code
  writes, byte for byte.
- **Errors:** a truncated or corrupt `.jxl` or `.ao.map`, a size that does not match the layout, a full disk: an error
  code and a message (a buffer the caller passes), the files removed; Python raises it as an `OSError` subclass, so
  Apply reports it per set, as today.
- **Build:** `build.cmd` compiles the DLL's source and zlib's in one `cl` process without `/MP` (or with `/MP12` at
  most), the same flags (`/O2 /fp:precise /MT /EHsc /std:c++17 /W4 /WX`; zlib's files may need `/W3` and no `/WX`).

## Session 7: Decision 4, Hand-Off, the PNG in C++

### Maintainer Decisions

- **Decision 4: the PNG writer may give other file bytes for the same pixels** (maintainer, 20261116). The C++ writer
  compresses blocks of the image on several threads; the pixels are the same as the Python writer's, the file's
  bytes are not (and it is slightly larger). Byte-identity, the rule of decision 3, holds for the pixels of every PNG
  and for the bytes of every other file.

### Why

`PngRowWriter` is zlib at level 6 on one core. The time is zlib's C code under Python, so C++ on one thread gains
nothing; only a compression split over threads does. An ORM texture of a whole set (4096 px, RGB, 16 bits, 96 MiB of
rows) takes several seconds. `read_png` unfilters Sub and Up rows in a Python loop and does not decode Average or
Paeth at all: such files (painting tools write them) are read through a temporary Blender image, which is slow and
holds the image as floats four times.

### What Moves to C++

New functions in `fss_ao_copy.dll` (interface version 3):

1. **The writer:** opened with the path, width, height, bits (8 or 16), channels (1 to 4) and threads; handed blocks
   of rows from the top (contiguous `(n, w)` or `(n, w, C)` integers in the file's depth, native byte order, any `n`);
   closed or aborted. The same file layout as `PngRowWriter`: signature, IHDR, filter 0 on every row, IDAT chunks,
   IEND. The filtered stream is cut into blocks at fixed byte offsets (not at the blocks Python hands in), each block
   compressed at level 6 on a worker thread with the 32 KiB before it as its dictionary and ended with a sync flush
   (the method of pigz), the last one finished; one zlib stream with its Adler-32. The file is therefore the same for
   any thread count and any blocking of the rows. A write copies the rows into a bounded queue and returns, so Python
   builds the next block while the workers compress; nothing in proportion to the image is held (auto-bake decision
   33). Abort, or an error, closes and removes the file.
2. **The reader:** fills a `(H, W, C)` uint16 array the caller passes (row 0 at the bottom, values in the file's
   depth, as `read_png` returns them) from grey, grey + alpha, RGB and RGBA files at 8 or 16 bits, with every filter
   (None, Sub, Up, Average, Paeth). Inflating is serial; unfiltering may run beside it. A palette, an interlaced file
   or another depth gives a format error, and Python falls back as today (its reader, then Blender).
3. **zlib:** deflate's source files of `native/third_party/zlib/` (already there, 1.3.2) compiled in as inflate's are.

`ao_bake_core.py` gets one place that picks the writer (for example `png_writer(path, w, h, bits, channels,
threads=None)`: the C++ writer when the DLL is loaded, else `PngRowWriter`), used by every site that creates a
`PngRowWriter` today (Apply's texture, the PNG masters when libjxl is missing, `ao_bake_native.py`); `read_png` tries
the C++ reader first. `PngRowWriter` and `PngRows` stay, unchanged, as the fallback. `FSS_AO_COPY=numpy` and a new
`FSS_AO_PNG=python` select the Python writer and reader. Apply's report says which wrote its texture as it says
`open` (a console line only when Python ran). Threads: Apply's Threads setting, as the copy and the opening take it.

### Rules for the DLL

The rules of Sessions 1 and 4 hold (C interface, error codes and a message buffer, no exception across the boundary,
`/MT`, no global state, a version function, the caller owns every buffer it passes; the writer's handle is freed by
close or abort). Also:

- **Same pixels:** every file the C++ writer writes decodes to exactly the rows handed in, by the Python reader, by the
  C++ reader and by Blender.
- **Deterministic:** the bytes of a C++-written file do not depend on the thread count or on how the rows were handed
  in.
- **Errors:** a full disk, a write to a folder that does not exist, a truncated or corrupt PNG: an error code and a
  message with the file's name; Python raises it as an `OSError` subclass, so Apply reports it per set, as today.
- **Build:** zlib's deflate files (`deflate.c`, `trees.c`) join the first `cl` call of `build.cmd`; the same flags
  otherwise. The DLL still depends on `KERNEL32.dll` only.

  - The writer: `fss_ao_png_open(path, W, H, bits, channels, threads, &writer, message, size)`, `fss_ao_png_write(writer,

  above 2 change nothing.
- `PngWriter` keeps its stats in `png_stats`, not `stats`: `MasterWriter` copies a writer's `stats` into the master's
  index entry, whose keys stay as they were.
- With the DLL, `read_png` raises `PngError` (an `OSError`) for a truncated or corrupt file; the Python reader raised

- `write_png_int` (the tests' writer of input files, "a PNG master as 0.55.2 wrote it") and the streaming `PngRows`

### What Moves to C++

  the masters already baked carry. A C++ part that changes them makes those masters re-grade once after the update.
- **Tests:** with the Python code gone, the tests check the C++ against results recorded from the Python code before
  it is removed (files and arrays in the tests' data), and against properties (same result at 1 and many threads,
  decoded pixels, counts).
