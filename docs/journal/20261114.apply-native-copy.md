# Apply's Copy in C++

Apply (AO Bake panel, `fss_blender_tools`) copies each object's master into the texture set's file. This journal
moves the copy's per-pixel work from numpy into a multithreaded C++ DLL. The bake, the masters and Apply's results
stay as they are; the design of Apply is in the auto-bake journal
([20261112.auto-bake-ao-curvature.md](20261112.auto-bake-ao-curvature.md), Sessions 17, 23, 35, 36).

measured more than 5 minutes for Apply of one object. Measured on a copy of the E2 cockpit (SEAT_OBS_SIT_FOAM, set

| Part of Apply (AO) | Seconds |
| :--- | ---: |
| Whole Apply of the AO | 70.7 |
| `copy_master` | 53.7 |
| of it, the inside pixels (`inside_step`) | 47.3 |
| of those, reading the master (`read`, `_surface_bilinear`, paged gathers) | 32.2 |

| the rest (padding, soften, PNG) | about 5 |

The curvature file of the same object took 68.4 s: the same copy again with other values. The panel also redrew
every 3D view after each 0.1 s of work; 0.75.1 redraws only the sidebar, which is not measured in an interactive
Blender yet.

### Maintainer Decisions

- **Decision 1: the copy in C++, multithreaded** (maintainer, 20261114). Apply's per-pixel work runs in a DLL loaded
  with ctypes, as the JPEG XL and OIDN libraries are. The numpy copy stays as the reference and as the fallback when
  the DLL cannot be loaded. A GPU version was considered and set aside: masters exceed a GPU texture's 16,384 px
  (SEAT_OBS is 16,638 px wide), the surface check, padding and soften would be rewritten as shaders, results could
  differ from the CPU's in the last bit, and the GPU is busy with Cycles bakes and an inference VM.
- **Decision 2: the source lives in this repository** (maintainer, 20261114): `native/ao_copy/`, the built DLL
  committed in `fss_blender_tools/lib/ao_copy/windows-x64/` like the JPEG XL DLLs. It follows libPolygone's runtime
  rules (C interface, memory owned by the caller, no exceptions across the boundary, no C++ runtime DLL,
  deterministic), but it is not part of libPolygone.

#### What Moves to C++

Per band, Python keeps what it does today up to the per-pixel loops: `copy_context`, the band raster at one sample
per pixel (`owner_c`, `count_c`), `dilate_ids`, the hinged neighbour triangles of padding pixels, `soften_context`,
`_soften` (it calls `read`; keep a Python `read` for it), the band bookkeeping and the PNG. The DLL does:

1. **Inside pixels:** for every pixel with an owner and its level L (`kt` of its owner): the L x L sub-sample owners
   exactly as `raster_window(uvpx, ..., L, ...)` gives them (every triangle tested in index order, the last one whose
   barycentrics are all at least -1e-9 wins, with `rasterize_ids`' integer bounding-box test before the barycentric
   test), the `outside_mode='tri'` rule, `barycentric_many`, `read` (the clamp into the island's rectangle or
   `rect_id`, `filled`, the barycentric clamp, `_surface_bilinear` with the face map, `tri_normal` and `surface_cos`,
   the plain `bilinear` fallback), the weighted mean, and the centre value when no sub-sample counts. Also the count
   of clamped points (`info['clamped_inside_points']`).
2. **Padding pixels:** given each padding pixel's source triangle and its hinged UV triangle, the L x L points
   (barycentrics clamped and renormalized), `read`, and the mean.

The master is read from the scratch page files `open_master` writes (tiles of `PAGE_TILE` px; uint16 AO, int32 map
codes), memory-mapped, or from whole arrays (`load_master`, tests). The DLL gets pointers, sizes and the tile layout;
it allocates nothing the caller has to free.

#### Rules for the DLL

- **Results byte-identical to the numpy copy.** Float64 throughout, the same formulas in the same operation order;
  `/fp:precise`, no FMA contraction, no fast-math. Where numpy reduces, reproduce its order: `np.add.reduce` over a
  contiguous axis uses pairwise summation (eight partial sums in blocks of 128 elements), so a mean of 64 sub-samples
  is not a plain loop; `np.einsum('nk,nkd->nd')` and the 4-tap sums must be checked the same way. Build a small
  harness that compares each C++ function with its numpy counterpart on random inputs, bit for bit, before
  wiring it into Apply.
- **Deterministic for any thread count:** each pixel's result depends only on its inputs; threads split pixels, never
  a pixel's sum.
- **Threads:** the bake's Threads setting (`scene.fss_ao_bake.threads`), at most 12.
- **C interface:** plain C functions and structs, error codes, no exceptions across the boundary, static C runtime
  (`/MT`), a version function. No global state.
- **Fallback:** when the DLL cannot be loaded, or `FSS_AO_COPY=numpy` is set, Apply runs the numpy copy. Apply's
  report says which copy ran.

### Built

- `native/ao_copy/`: `fss_ao_copy.h` (C interface, `fss_ao_master` with 8-byte fields only), `fss_ao_copy.cpp`,
  `build.cmd` (`cl /O2 /fp:precise /MT /EHsc /std:c++17 /W4 /WX /LD`, one compiler process, no `/arch:AVX2`),
  `README.md`. Output `fss_blender_tools/lib/ao_copy/windows-x64/fss_ao_copy.dll` (152,576 bytes; dumpbin: only
  `KERNEL32.dll`, no FMA instruction). Intermediates in `native/ao_copy/build/`, git-ignored (`.gitignore`). Built
  under `cpucap.exe 50`.
- Exports: `fss_ao_copy_version` (1), `fss_ao_copy_inside`, `fss_ao_copy_padding`, and the test entry points
  `fss_ao_copy_read`, `fss_ao_copy_raster`, `fss_ao_copy_sum`. Error codes, no exception across the boundary, no
  global state; threads take chunks of 64 pixels from an atomic counter, a pixel's sums never split.
- The inside pixels: per pixel the owner's L x L sub-samples. A sub-sample's owner follows rasterize_ids' rule (the
  last triangle whose integer sample box contains the sample and whose barycentrics are all at least -1e-9) on the
  grid that starts at the corner of the pixel's block: Python passes that corner per pixel, the blocks formed as
  `copy_master` forms them, so the sample positions round as numpy's do. Only the owner and the triangles after it in
  a bin of 8 x 8 px are tested. Then `barycentric_many`, `read()` (the island rectangle and `filled`, the barycentric
  clamp, `_surface_bilinear` or plain `bilinear`), the weighted mean, the centre value when no sub-sample counts, and
  the count of clamped points. The padding pixels: the L x L points in the given UV triangle, clamped and
  renormalized, `read()`, the mean.
- numpy's orders, measured with Blender's numpy 2.3.4 (`tests/_work/ao_copy/order_probe.py`) and reproduced:
  `np.add.reduce` of a contiguous axis is 0 plus the pairwise sum (eight partial sums up to 128 values, halves above);
  `np.einsum('nk,nkd->nd')` is `(p0 + p1) + p2`; `np.einsum('nd,nd->n')` is `(p0 + p2) + p1` (its two-lane SIMD
  accumulator); the float to int64 cast gives INT64_MIN for NaN, as cvttsd2si does.
- `fss_blender_tools/ao_bake_copy.py`: loads the DLL with ctypes (version check); `backend()` (`FSS_AO_COPY=numpy`,
  or the DLL not loaded: numpy with the reason); `prepare()` (a paged master: its two page files memory-mapped
  read-only; a whole master: the image, and its filled mask and face map packed into map codes, once per master
  dict); the calls; errors as `CopyError` (an OSError, so Apply reports them per set).
- `ao_bake_core.py`: `native_copy()` (imported as `jxl()` imports its module); `PagedArray.address()` (the page file
  mapped, unmapped by `close()`); `copy_master(..., threads=None, backend=None)`: the inside and padding loops call the
  DLL when it runs, else the numpy code, unchanged; `info['copy']`, `copy_why`, `copy_threads`. The DLL runs for
  outside_mode `'tri'`, not same_face, a uint16 master without `rect_id`, levels up to 64; otherwise numpy. The
  per-pixel Python loop of the padding's hinged triangles is now one `_hinged_uv` per distinct (triangle, edge),
  mapped back (both copies).
- `ao_bake_apply.py`: Apply passes the bake's Threads setting (the DLL takes at most 12); the report has `copy`
  (`C++ (12 threads)` or `numpy (why)`), and its lines add `copy: numpy (...)` only when numpy ran (see Not Verified).
- Tests: `tests/test_ao_copy_native.py` (the harness, plain Python with Blender's numpy, listed in tests/README.md);
  `test_native_copy` in `tests/test_ao_bake.py` (after `test_curvature_only`); `test_soften_edges` also compares the
  two copies on its hand-built master, softened. `tests/_work/ao_bake/apply_prof/apply_prof.py` (copied from Session
  1) takes `copy=numpy|native`, `tag=`, `prof=0|1`, keeps each output as `out_keep/<kind>_<tag>.png` and prints the
  parts.
