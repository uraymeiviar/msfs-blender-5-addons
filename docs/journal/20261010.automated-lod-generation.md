### Problem Statement

The FSS E-Jet models have only LOD0 (see the 2026-10-01 LOD journal). Making LODs by hand is the step artists dislike most: every part, every level, kept consistent with node names, animations and textures. The goal is to generate all LODs from LOD0 automatically, at the best quality available, with CPU and GPU time not a constraint.

Plain decimation is not enough. It tears UV seams, breaks shading normals, collapses thin parts and changes the silhouette. A LOD does not need clean quad topology (it is never edited or subdivided); it needs the same silhouette, intact UV seams, sane normals, no holes, and the same node names and animations.

### SDK Constraints

- MSFS picks a LOD by the bounding sphere's height as a percentage of the screen, against each `<LOD minSize>`. **[SDK]** (LOD Selection System (FSS aircraft repository `doc/msfs-sdk/pages/models-and-textures/modeling/lods/lod-selection-system.md`))
- A LOD with too many vertices for its size on screen is skipped. **[SDK]** (Aircraft Modeling General Principles (FSS aircraft repository `doc/msfs-sdk/pages/models-and-textures/modeling/aircraft/aircraft-modeling-general-principles.md`))
- The SDK's aircraft table sets triangles, materials and textures per LOD, from 1,500,000 triangles and 65 materials at x0 down to 100 triangles and 1 material at x6 (summarised in the authoring guide (FSS aircraft repository `doc/msfs-authoring/lods.md`)).
- Keep the silhouette and high-contrast details in every LOD. **[SDK]** (Silhouette and Material Contrast (FSS aircraft repository `doc/msfs-sdk/pages/models-and-textures/modeling/aircraft/airframe/silhouette-and-material-contrast.md`))
- The SDK's AutoLOD (Simplygon in the package build) works only for ModelLib (scenery) models, needs a licensed Simplygon SDK, and the SDK states hand-made LODs always beat it. **[SDK]** (Using Simplygon to Generate LODs (FSS aircraft repository `doc/msfs-sdk/pages/models-and-textures/modeling/landscape/using-simplygon-to-generate-lods.md`))
- Asobo's bundled `lod_tools_msfs_2024` add-on does LOD setup and visualization (LOD viewer, vertex counts, limits, LOD camera). It does not generate LODs (checked in `tools/blender/5.2/scripts/addons_core/lod_tools_msfs_2024/`).

The 2026-10-01 LOD journal proposes screen-size ranges and reduction percentages that differ from the SDK table above (for example LOD01 at 40% to 15% screen size, where the SDK table has x1 at 75%). This session follows the SDK table; the earlier figures need review.

### Proposed Approach

Do not write a simplifier. Fork flow-lod (MIT) for the per-object pipeline, keep Blender Decimate as the main reduction core, add meshoptimizer for parts that need attribute weights and locks, and build an MSFS layer on top.

| Layer | Source |
| :--- | :--- |
| Per-object repair, clean, hidden-face removal, deviation budgets, normal bake, impostor, CLI, tests | flow-lod (fork) |
| Reduction core | Blender Decimate; meshoptimizer for skinned or seam-heavy parts, compared side by side |
| MSFS layer | Whole hierarchies; node names and NLA tracks kept; small-feature removal by pixels covered at the LOD's `minSize`; SDK per-LOD budgets; merge and atlas at LOD3 to 4; proxy remesh and bake at LOD5 to 6; dirt mesh regeneration (wish-list item 19); cockpit LOD1 from window visibility (item 21) |
| Quality measurement | Render LOD0 and each candidate at the exact switch screen size from many angles (silhouette masks and shaded images), score with a perceptual metric such as NVIDIA FLIP, and search each part's reduction for the strongest one under the error threshold; parts that never reach it are flagged for the artist |
| LOD setup and visualization | Integrate with `lod_tools_msfs_2024`, do not duplicate it |
| Benchmark | A Simplygon evaluation licence, used once to compare results |

Expected results by part:

| Part | Expectation |
| :--- | :--- |
| Exterior LOD1 to 3 | Mostly automatic; skinned wing parts need weight-preserving simplification |
| Exterior LOD4 to 6 | Automatic: proxy remesh and bake |
| Cockpit LOD1 | Automatic with window visibility, then aggressive reduction |
| Animated mechanisms (gear linkages, doors) | Semi-automatic: the tool flags, the artist checks the motion |

### No AI Agent in the LOD Pipeline

The LOD export and the LOD tool are deterministic: they run inside the deploy in a background Blender, on any artist's PC, and the same `.blend` always produces the same LOD files. No step depends on an AI agent or on parameters an agent sets.

- An agent rebuilding meshes through Blender MCP was considered and rejected: placing thousands of vertices through tool calls is slow and imprecise, and a rebuilt mesh loses the LOD0 UVs and textures.
- Part decisions (keep, drop, merge, replace) come from rules and the artist's marks (Session 2), not from an agent.
- An agent may help an artist outside the pipeline (proposing marks, reading the LOD report), as optional assistance only.
- Research models that generate low-poly meshes (for example MeshAnything, 2024) were not evaluated.

## Session 2: Design for Stage 1 and 2: Per-LOD Export from Marks and Automatic Size Culling

- **Date:** 20261016
- **Developer:** uraymeiviar
- **Agent:** Claude Code (Opus 5.5)
- **Branch:** dev/fs24/uray
- **Base Commit SHA:** 28e8a39606d650dde1a2f818548daedb74292556 (2026-10-16 11:47:18 +0700); add-on repository `msfs-blender-5-addons` at 7e686e4

> [!NOTE]
> **Design handoff:** this session records the agreed design for an implementing agent. Nothing in it is built yet.

### Problem Statement

The E-Jet models have only LOD0. Artists cannot build thousands of objects times six LOD levels by hand, even with tooling. MSFS selects a whole glTF per LOD by the model's bounding sphere on screen (Session 1, SDK Constraints); it never hides individual nodes inside a file. So making parts disappear at lower detail is the exporter's job: every LOD file must contain only the parts that are still worth drawing at the screen sizes that file is shown at.

fss-blender-tools already lets artists mark an object's LOD level (`lod.py`, custom property `fss_lod`, 0 to 6) and filter the viewport by LOD, but the deploy still exports one file, and the marking's meaning is inverted (below).

### Key Insight: the Merge Tree Keeps Part Boundaries

Because `@MERGE_` groups keep every part a separate object in the `.blend` and only join them at export, the exporter knows the part boundaries. Per LOD file it can leave whole parts out first and merge what remains afterwards, so `_LOD00` merges a panel with its screws and `_LOD04` merges the panel without them. No geometry is cut, so no holes, torn edges or broken UVs appear; every boundary is one the artist modelled. Artists model naturally, as separate parts; LODs follow from size, and marks are exceptions.

### Maintainer Decisions

1. **The mark means "hidden from LOD n".** An object marked 3 is in `_LOD00` to `_LOD02` and absent from `_LOD03` on. The current code implements the opposite (at viewport LOD 3 it hides marks 4 to 6, so a mark 3 is shown from LOD 3 on) and must be corrected.
2. **The reverse mark exists for replacement meshes:** "visible from LOD n" (absent from `_LOD00` to `_LOD(n-1)`, present from `_LODn` on). The replacement workflow and UI are not designed yet; stage 1 only needs the mark.
3. **The default for every object is "auto":** an unmarked object is auto, and the exporter decides by size when it starts to be hidden. Explicit marks override auto.
4. **File naming `<name>_LODxx.gltf`**, two digits, `_LOD00` the full model.
5. **The export settings include an explicit "whole" (reference) size,** for models whose LOD switch uses a larger sphere than the exported file's own (for example a glTF merged into another model at runtime with `<MergeModel>`). Otherwise the reference is computed.
6. **Polygon reduction of large parts is a later stage** (stage 3); stages 1 and 2 only include or leave out whole parts.
7. **`fss_lod` keeps its name with the corrected meaning** ("hidden from LOD n"); the existing marks were set with that intent, so no conversion.
8. **One `.blend` writes all seven files, `_LOD00` to `_LOD06`, to one deploy target, always.** The export settings live per scene. Merged submodels (`<MergeModel>`) therefore always have a file for every LOD of their base model.
9. **The deploy base name drops the `-LOD00` suffix** (for example `E195-Cockpit`, written as `E195-Cockpit_LOD00.gltf` to `E195-Cockpit_LOD06.gltf`); the deploy `.bat` arguments and the model XML `<LODS>` entries change once.
10. **Defaults:** `minSize` table by model type (SDK aircraft table for exterior parts; a cockpit table for interiors, whose LOD0 is forced inside and whose LOD1 and below are only seen through the windows; scenery editable); quota at the High graphics setting; 1440 px reference screen height; 2 px threshold.
11. **Keep can also come from tags:** a per-tag Keep toggle in the Tags list, like the Don't Merge toggle.
12. **Stage boundary:** stage 1 is the marks with auto doing size culling, the corrected viewport filter, the per-LOD export and its console report; stage 2 is the quota and hints panel and the auto viewport LOD.

### Object Marks (stage 1)

Each object carries one LOD mode, stored as custom properties so a `.blend` stays readable without the add-on:

| Mode | Stored as | In `_LODk` |
| :--- | :--- | :--- |
| Auto (default) | no property | decided by size (Automatic Size Culling) |
| Hidden from n (1 to 6) | `fss_lod = n` | present for k < n |
| Visible from n (1 to 6) | `fss_lod_show_from = n` | present for k >= n |
| Keep | `fss_lod_keep = 1` | present in every LOD, never culled by size |

- `fss_lod` keeps its name; only the code's interpretation is corrected (decision 7). The two new modes get their own properties. A Keep tag (decision 11) has the same effect as `fss_lod_keep`.
- **Parent rule:** a child can never be present where its parent is absent; a hidden parent takes its subtree out of that LOD file. The effective hide-from of an object is the minimum of its own and all ancestors' hide-from values, and its effective show-from the maximum. The UI clamps on assignment and reports clamped objects, as the current top-down clamp does, with the direction corrected.
- Animated, skinned, `@NOMERGE_` and tagged objects are culled like any other part; their animation simply has no node in that LOD file, which is normal for MSFS LODs.

### Automatic Size Culling (stage 1)

At export time the exporter knows the screen sizes each LOD file is shown at, because it uses the same `minSize` table that goes into the model XML. `_LODk` is shown only while the model's bounding sphere covers between `minSize(k)` and `minSize(k-1)` of the screen height. The largest a part of `_LODk` ever appears is therefore at `minSize(k-1)`.

A part (object together with its whole subtree) is left out of `_LODk` when:

> part size / reference diameter < threshold px / (minSize(k-1) x screen height px)

- **Part size:** the largest dimension of the part's subtree's world bounding box (conservative: a long thin cable stays while its length is visible).
- **Reference diameter:** the bounding-sphere diameter of everything exported into `_LOD00` of that glTF, or the explicit reference size when set.
- **Subtree rule:** a part is culled only if its whole subtree is below the cut-off, so a small parent with a large child stays.
- **`minSize(0)` for `_LOD01`:** LOD0 starts at 100 % or more of the screen height; the formula uses 100 %.
- **Explicit marks override auto;** Keep is never culled.

With the SDK aircraft `minSize` values (100, 75, 55, 35, 8, 5, 1), a 1440 px screen height and a 2 px threshold, a part is culled below these fractions of the reference diameter (and on a 3 m model):

| File | Shown up to | Culled below | On 3 m |
| :--- | :--- | :--- | :--- |
| `_LOD01` | 100 % | 0.14 % | 4 mm |
| `_LOD02` | 75 % | 0.19 % | 6 mm |
| `_LOD03` | 55 % | 0.25 % | 8 mm |
| `_LOD04` | 35 % | 0.40 % | 12 mm |
| `_LOD05` | 8 % | 1.7 % | 5 cm |
| `_LOD06` | 5 % | 2.8 % | 8 cm |

Limits: size says nothing about occlusion (a large hidden part stays; window visibility is wish-list item 21); small but important parts (annunciators, emissive LEDs) need Keep; the in-sim Object LOD quality setting shifts `minSize`, so the table assumes the neutral "high" setting (SDK); parts already joined into one mesh in Blender cannot be culled separately (a later extension can treat disconnected islands as parts).

### Vertex Count Limits

MSFS applies a second rule on top of `minSize`: "the effective `minSize` used by the simulation is the maximum value between that specified in the XML and that calculated from the curve" of vertex count against screen size (SDK, `modeling/lods/lod-selection-system.md`). A LOD file that has too many vertices for the current screen size is skipped and the next LOD is tried. Part of the SDK table at the High graphics setting (the curve shifts with the setting; tune at High):

| Vertices in the LOD file | Minimum screen size (High) |
| :--- | :--- |
| 5,000 | 2 % |
| 30,000 | 12 % |
| 60,000 | 24 % |
| 150,000 | 60 % |
| 250,000 | 100 % |
| 500,000 | 141 % |
| 1,000,000 | 200 % |

Also from the SDK: below 0.1 % of the screen nothing is drawn; the last LOD's `minSize` is forced to 0.1 %; the second-to-last is forced to at least 1 %, except for the user aircraft.

Consequences for this design:

- **Cut-offs use the effective `minSize`:** the upper end of `_LODk`'s range is `max(minSize(k-1), curve(vertices of _LOD(k-1)))`, not the XML value alone. A dense previous LOD stays out until a larger screen size, so `_LODk` can appear larger than the XML suggests; using the XML value alone would cull parts that are still visible. The exporter builds the LODs in order, so the vertex count of `_LOD(k-1)` is known when `_LODk` is decided.
- **Per-LOD report:** vertex count, the screen size the curve requires at High, the intended range from the `minSize` table, and a warning when MSFS would skip the file or take it over later than intended, for example `_LOD02: 180 000 vertices -> allowed from 66 % (High); intended from 55 % -> skipped between 55 % and 66 %`.
- **Size culling alone is not enough for dense models:** large parts keep every vertex, so the middle LODs of a cockpit can stay above the curve and be skipped. Stage 3 (polygon reduction) is what makes them usable; the report shows where it is needed.
- **Reference implementation:** the LOD Tools add-on implements the curve (`lod_tools_msfs_2024/lod_limits.py`, `lowest_screen_size_from_vcount`, `max_vertex_count`); reuse it rather than a copied table.
- **Production figures (E195, High setting):**

  | Model | Files | Vertices | LOD allowed from (screen height) |
  | :--- | :--- | :--- | :--- |
  | Exterior | `E195-Exterior-LOD00` with merged `E195-Exterior-Wings-LOD00` | 355,268 + 577,037 = 932,305 | about 192 % |
  | Interior | `E195-Cockpit-LOD00` with merged `E195-Cabin-LOD00` | 820,853 + 2,492,758 = 3,313,611 | beyond the table (over 282 %) |

  The E2 cockpit alone has 1,325,733 vertices (about 227 %).
- **Interior from the seat:** the aircraft's `model.cfg` sets `withInterior_forceFirstLod=true` ("when showing the interior, force showing lod0"), so inside the cockpit the interior's LOD0 is shown regardless of its vertex count.
- **Interior from outside:** `withExterior_showInterior=true` draws the interior in exterior views, and both of its LOD entries use the same full files, so every exterior view also draws the full cockpit and cabin. This is the strongest case for interior LODs (window visibility, wish-list item 21, plus stages 1 to 3).
- **Defect in `E195_EXTERIOR.xml` (confirmed in the sim by the maintainer: the chocks and cones are only visible when the aircraft fills most of the screen):** the exterior has two LOD entries with the same files, the first (`minSize="5"`) with the ground-object attachments, the second (`minSize="0"`) without. With 932,305 vertices the first entry's effective `minSize` is about 192 %, so MSFS normally skips it and uses the second, and the chocks, cones and engine covers only appear when the aircraft is very large on screen. Fixes: attachments on both entries, or lighter exterior LOD files.
- **Per-part budgets:** separate models (each with its own `<LODS>`) are judged on their own bounding sphere and vertex count; a `<MergeModel>` submodel is expected to count together with its base model (not verified in the SDK).
- **First LOD build, checks in DevMode Debug LODs:** the cockpit reports LOD0 from the seat; from outside it switches to `_LOD01` at the expected size; attachments on LOD entries appear where intended.
- **Not verified:** whether MSFS counts vertices as the glTF stores them (split at UV seams and hard edges) and how instances count; the report must state which count it uses.

### Quota and Hints (artist workflow)

Hiding whole parts is the primary way to meet the vertex limits; polygon reduction (stage 3) is secondary. A dropped part removes exactly its vertices, so the result is predictable and under the artist's control.

- **Quota per LOD:** the most vertices `_LODk` may have and still be shown from its own `minSize`, from the SDK curve at High (for example about 85,000 for a LOD meant to show from 35 %). LODs forced by `withInterior_forceFirstLod` are reported as forced.
- **Panel:** per LOD, the vertex count, the quota, the percentage, and an over-quota warning, for example `_LOD02  160,000 / 137,000  117 %  OVER`.
- **Hints for an over-quota LOD, each with a Select button:**
  - the largest contributors: objects and merge groups with the most vertices present in that LOD;
  - hidden potential inside a mesh: disconnected pieces (loose parts) below that LOD's size cut-off and the vertices they hold, for example "`PEDESTAL_SHELL`: 214 loose parts below 12 mm, 38,000 vertices; separate them and they drop out of `_LOD04`". This guides the main workflow: split such pieces into separate objects, and the size rule removes them;
  - near the cut-off: objects just above a LOD's cut-off that cost many vertices, candidates for a "hidden from LOD k" mark.
- **Loop:** Refresh, pick a hint, split or mark, Refresh, until every LOD fits; then deploy. The panel and the export use the same decision function, so the export writes exactly what the panel showed.
- **Vertex counting as in the glTF:** vertices are split where UVs or normals differ, so the tool counts unique combinations of position, normal and UV per corner of the evaluated meshes; Blender's own vertex count would make the quota optimistic.
- **Cost:** counting a cockpit's evaluated meshes for every LOD is too slow for a redraw; it runs on Refresh and is cached, like the Merge Tree.

### Export Flow

1. The deploy script (`scripts/export-blend-to-gltf.py`) exports seven times. For each LOD k (0 to 6) it sets a scene-level "LOD being exported" value, runs the export as today, and writes `<name>_LODkk.gltf`.
2. The pre-export hook of fss-blender-tools (the merge module, on the multi-exporter's throwaway copies) first removes every object that is absent from LOD k (marks, parent rule, size culling), then merges `@MERGE_` groups as today. The merge already only walks exported objects, so culled parts are simply not merged.
3. The reference diameter is computed once from the LOD0 export set and reused for every LOD.
4. `deploy-gltf.bat` copies `%TARGET_FILENAME%.gltf/.bin` today; it must copy all seven `_LODxx` files. The base name drops today's `-LOD00` suffix (decision 9), so the deploy calls and the model XML `<LODS>` entries change once.
5. Per-LOD merge and cull reports go to the console like the merge report, one line per LOD: objects in, culled by mark, culled by size, merged meshes.

### Viewport LOD

- Fix the filter to the "hidden from" meaning (viewport LOD k shows exactly the objects of `_LODk`), using the same decision function as the export, so the viewport and the exported files can never differ.
- **Auto viewport LOD (stage 2):** compute the model's bounding-sphere screen ratio from the active 3D viewport (vertical field of view and distance), pick the LOD from the `minSize` table, and apply the filter only when the LOD changes, not on every redraw. The LOD Tools add-on implements the same screen-size and vertex-limit formulas (`lod_tools_msfs_2024/lod_limits.py`) and is the reference for consistency.
- The current filter uses `hide_set` and a marker property (`_fss_lod_hidden`); keep restoring exactly what it hid.

### Implementation Notes

- **Trap: objects hidden by the viewport LOD filter.** The filter hides objects with `hide_set`, and the deploy exports only visible objects; a `.blend` saved while the filter is active would silently lose every hidden part in all seven files. The export must treat objects marked `_fss_lod_hidden` as visible (or clear the filter first).
- **Model type:** a scene setting (Exterior part, Interior, Scenery) selects the default `minSize` table.
- **Interior table (from the SDK cockpit LOD correlation):** cockpit x0 is the interior view (forced inside by `withInterior_forceFirstLod`); cockpit x1 to x5 are shown while the exterior shows x0 to x4; nothing matches exterior x5 and x6, so `_LOD06` of an interior culls everything. A cockpit `minSize` refers to the cockpit's own bounding sphere, so `cockpit minSize(k) = exterior minSize(k) x cockpit diameter / exterior diameter` for k = 1 to 5. Interiors need one extra setting, the exterior model's diameter, because the cockpit `.blend` does not contain the exterior. Example E195 (exterior about 40 m, cockpit about 3.5 m): x1 about 6.6 %, x2 4.9 %, x3 3.1 %, x4 0.7 %, x5 0.45 %.

The fs20 table defaults to the fs24 values and is marked unverified: the 2024 SDK only says that packages built for MSFS 2020 follow the legacy LOD rules. The vertex-count correction is an MSFS 2024 rule and is off for fs20; fs20 instead forces the second-to-last LOD's `minSize` to at least 1 %, as the 2024 SDK describes for earlier versions. Check in MSFS 2020's LOD debug view before relying on it.
- **Vertex count of the previous LOD** (effective `minSize`): read it from the `_LOD(k-1)` glTF just written (sum of the `POSITION` accessor counts); exact, no estimate.
- **Vertex curve:** copy the curve constants into fss-blender-tools with a reference to `lod_tools_msfs_2024/lod_limits.py`; fss-blender-tools stays independent of the Asobo add-ons (repository `AGENTS.md`).

> [!NOTE]
> **Design amendment:** the implementing agent raised four questions; the maintainer's answers below extend the Session 2 decisions. Decisions 15 and 16 supersede Session 2 statements, listed under each.

### Maintainer Decisions (continued)

13. **Keep wins against size culling, explicit marks win against Keep.** An Auto object stays in every LOD where any of its descendants is Keep; only the ancestor chain stays, its other small Auto children are still culled. This follows from the subtree rule (a part is culled only if its whole subtree can be culled) and does not conflict with the parent rule, which only applies once a parent is absent. An explicit "hidden from n" on an ancestor still removes the Keep child from LOD n on; the report warns "Keep under hidden ancestor".
14. **Exterior diameter for interiors is required only by the derived table.** While an interior uses the derived default `minSize` table, a positive exterior diameter is required: if it is missing, the export of that model stops with a clear error and the preview shows "exterior diameter missing". There is no fallback to the exterior table, because on the cockpit's small sphere it would switch the cockpit LODs far too early. A hand-edited interior table is explicit and needs no diameter. The diameter is set once per scene and saved in the `.blend`.
15. **Size culling uses the XML `minSize` table only, never the effective `minSize`.** Which objects are in `_LODk` then depends only on marks, sizes and the table, so the preview and the export select identical objects by construction, without scratch exports. Vertex counts are report-only: quota, percentage, OVER warnings and the effective `minSize` line of the console report. The panel shows an estimate, labelled as such (counted per material primitive, including the attributes actually exported); the export console report gives the exact `POSITION` count from the written files. Refresh does not export.
    - **Supersedes** in Session 2: "Cut-offs use the effective `minSize`" (Vertex Count Limits) and "Vertex count of the previous LOD" (Implementation Notes).
    - **Accepted consequence:** when `_LOD(k-1)` is over its quota, MSFS shows it only from a larger screen size, so `_LODk` is seen larger than planned and a part culled by size may be noticeable. That case is reported as OVER and is fixed by the artist with the hints; culling does not compensate for it.
16. **Empty LODs are not written.** The exporter writes `_LOD00` up to the last LOD that still has objects; the first LOD with no objects ends the list and nothing after it is written. The `<LODS>` snippet and the console report end at the last written file, and the report states "`_LODkk`: not written, no objects". `deploy-gltf.bat` copies whichever `_LODxx` files exist. Every written file goes through the multi-exporter; there is no plain-exporter path for fs24.
    - **Why:** the MSFS 2024 multi-exporter rejects an export with no objects, and whether MSFS accepts a glTF without meshes as an LOD is not verified. The SDK cockpit LOD page expresses the same thing as fewer LODs: the cockpit has no LODs matching exterior x5 and x6.
    - **Supersedes** in Session 2: decision 8 ("always `_LOD00` to `_LOD06`"), and "`_LOD06` of an interior culls everything" (Implementation Notes): the interior's list ends at `_LOD05` instead.
    - **Visible-from marks:** objects marked "visible from n" can make a LOD after an empty one non-empty. The list still ends at the first empty LOD, and the report warns about the objects left out.
    - **Accepted consequence:** MSFS forces the last listed LOD to `minSize` 0.1 %, so a cockpit ending at x5 is still drawn while tiny instead of disappearing; the SDK considers that size unnoticeable.
    - **Stale files:** a `_LODxx` file from an earlier export can remain in a deploy target. The XML does not reference it, so it is harmless; the report names it, and nothing deletes files in the live projects.

### Implemented

- **`fss_blender_tools/lod_model.py`:**
  - `mesh_pieces(evaluated_obj, mesh, scale)`: Vectorized numpy connected-component analysis over evaluated mesh edges (`mesh.edges` union-find with path compression) and world-space bounding-box largest dimension per component (`np.minimum.at` / `np.maximum.at`). ## Session 16: Bounding Sphere Padding Measured, Not Reliable

- **Date:** 20261017
- **Developer:** uraymeiviar
- **Agent:** Claude Code (Opus 5.5)
- **Branch:** main
- **Base Commit SHA:** f7ee6fc

### Test

- Idea (decision 25, open proposal): enlarge the cockpit's bounding sphere by k with invisible padding and multiply the XML `minSize` table by k, so the XML instead of the vertex curve decides the LOD switches. Padding: a root node `FSS_LOD_PADDING` with two degenerate triangles (three identical corners each, zero area, never rasterised) at opposite corners of a box centred on the cockpit, material `InvisibleCollider` (`ASOBO_material_invisible`). MSFS's package compiler requires the `ASOBO_unique_id` extension on every node once a file uses it (`{"id": "<node name>"}`); without it the build fails.
- Measured in DevMode Debug LODs, E2 cockpit, same camera settings each time (Fixed look, Reset position, zoom level 50):

  | Variant | Box diagonal | Seat view `Size` | Default external view `Size` |
  | :--- | ---: | ---: | ---: |
  | No padding | 4.43 m | 586.74 % | 6.10 % |
  | k = 5 | 22.2 m | 216.38 % | 28.80 % |
  | k = 35 | 155.2 m | 216.38 % | 28.81 % |

- With k = 35 an external view selected `_LOD03` exactly at the XML value (`Size` 114.26, `MinSize` 106.75), but the seat view selected `_LOD03` as well (`Size` 144.35 there, other camera settings), so the interior needed `withInterior_forceFirstLod=true`.

### Findings

- Padding changes `Size`, but the effect saturates (k = 5 and k = 35 give identical values although the drawn sphere differs sevenfold), lowers the seat-view size instead of raising it, and fits no formula based on sphere radius and camera distance. MSFS's screen-size computation for enlarged spheres, and for cameras inside the sphere, is unknown.

### Maintainer Decisions (continued)

28. **Padding the bounding sphere is not used** (decision 25 closed): it influences LOD selection in a way that is undocumented, saturates and cannot be predicted, so switch timing cannot be tuned reliably with it.

### State Restored (E2 test package)

- All six cockpit LODs: the unpadded, unreduced deploy; `E2_190_INTERIOR.xml` with the derived interior table (100 / 6.53 / 4.79 / 3.05 / 0.70 / 0.44); `model.cfg` `withInterior_forceFirstLod=false` (the seat view selects `_LOD00` by size: 586 % against 228 %).
