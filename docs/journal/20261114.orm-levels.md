# ORM Levels: Per-Texture Adjustments Applied at Export

Levels for the channels of an MSFS material's Occlusion/Roughness/Metallic texture and its detail ORM texture: set
in Blender, previewed by shader nodes, and applied to the image the exporter writes. The texture files in the
artist's project are never changed.

### Why

On the E2 cockpit's seat foam (`MAT_LEATHER`) the baked AO did not show. The material's detail ORM texture
(`Leather_comp.png`, 2048 px, tiled 10 x) has a red channel of about 1.0 (median 0.99), and MSFS adds
`(2 x detail - 1) x vertex alpha` to each ORM channel (MSFS 2024 SDK, Flightsim Material Textures, Detail
Occlusion(R) Roughness(G) Metallic(B): 0.5 is neutral). The occlusion was raised by about +0.98, so the AO turned
white. No glTF parameter scales the detail ORM per channel (`ASOBO_material_detail_map` holds only the textures,
`UVScale`, `blendThreshold` and the detail normal's scale); vertex alpha scales every detail map at once. Correcting
the texture needs an external image tool today. The maintainer asked for adjustments inside Blender.

Found on the way and fixed in the uncommitted tree (`material_preview.py`, deployed): Asobo's ORM group dropped the
texture's red without a detail texture (a constant 1), and Asobo's Apply AO group hid the AO wherever the viewport
light was above about 0.475. The preview now multiplies the base colour by the occlusion always.

### Decisions

1. **Adjusted at export, not by writing a new texture file.** The artist's texture files stay as they are; the
   exporter reads the original, applies the levels and writes the result. Writing an adjusted copy in the project was
   rejected as intrusive.
2. **The same file name.** The exported texture keeps the original's name; no renamed copies.
3. **Stored per texture, not per material.** The settings live on the image datablock, so every material using a
   texture shares them, and one file name holds one filtered version (a texture shared to save VRAM stays one
   texture). Changing a value in one material's panel changes every material that uses the texture.
4. **Full Levels, five values per channel:** input black, gamma, input white, output black, output white. Per
   texture: occlusion, roughness and metallic each have their own five. Defaults (0, 1, 1, 0, 1) change nothing.
   Formula, per channel value `x` in 0..1:
   `t = clamp((x - in_black) / (in_white - in_black), 0, 1)`, `out = out_black + (out_white - out_black) * t ^ (1 / gamma)`.
   When `in_white <= in_black`, `t` is 1 where `x >= in_black`, else 0.
5. **UI:** in the MSFS material panel's area, under the ORM and detail ORM texture slots: per channel a histogram of
   the texture's values with markers at input black, gamma (the midpoint) and input white, and the result's range
   shown; the three input sliders under it, then the two output values. A note says how many materials share the
   texture.
6. **Preview by shader nodes only:** in every material that uses the texture, FSS nodes between the texture and what
   reads it apply the formula. They are always in the tree (defaults pass the image through) and are refreshed when
   a value changes and when a file opens.

| Path | ORM | Detail ORM | Bytes written |

The glTF image maps back to its Blender image through the `ExportImage` passed to `gather_image_hook`: each fill holds

### Built

- `io_scene_gltf2_msfs_fss/orm_levels.py` (new, FSS-owned):
  - `Image.fss_orm_levels`: three `FSS_ORMChannelLevels` (occlusion, roughness, metallic), each input black, gamma,
    input white, output black, output white; defaults 0, 1, 1, 0, 1. A change updates every MSFS material whose ORM or
    detail ORM texture node shows the image.
  - `levels_float` / `apply_levels`: the formula of decision 4, used by the filter (rounding to the nearest integer,
    halves up).
  - Preview: a group node `FSS ORM Levels` / `FSS Detail ORM Levels` (group `.FSS ORM Levels v1`) between the texture
    node and every reader of its colour. The group is Vector Math only (multiply-add, clamp, power, multiply-add):
    Khronos takes a channel from the last Separate Color on its way back to the texture, so a Separate Color in the
    levels would change what File > Export writes. Input white at or below input black is a 1e-5 wide ramp below
    input black.
  - Export: `filter_gltf_image` replaces the bytes of a PNG whose channels all come from one image with levels
    (Khronos' happy path) by the filtered PNG: decoded by Blender from a temporary file (read as data, alpha as it is;
    exact for 8 and 16 bits), R, G, B filtered, written with the same size, bit depth, colour type, alpha and
    ancillary chunks (rows filtered by PNG's usual heuristic, zlib level 6). Not filtered, with a warning: a composed
    image, a non-PNG, a palette or below-8-bit PNG, a grey PNG whose three channels have different levels, Keep
    Original. A cache keyed by the SHA-1 of the source bytes and the 15 values (16 entries) filters a texture once
    across presets and exports.
  - Panel `draw`: a collapsed "Levels" layout panel under the slot (header "Levels (adjusted)" when changed), the
    number of material slots sharing the texture, per channel a histogram icon (128 px, two bins per column, markers at
    input black, the gamma midpoint and input white, the range outside dimmed), the range of the texture and of the
    result, the three input sliders, then the two outputs. The histogram reads the image's pixels in memory (256
    levels), cached per image and file path, size and modification time; the icon is a `bpy.utils.previews` image (not
    ID data).
- Marked hooks in Asobo's files: `_update_omr_links` ends with `orm_levels.apply(self)` (and its import) in
  `blender/material/msfs_material.py`; `draw_omr_texture_prop` and `draw_detail_omr_texture_prop` in
  `blender/utils/msfs_material_utils.py` call `orm_levels.draw`. Opening a file rebuilds every MSFS 2024 tree, which
  runs `_update_omr_links`.
- FSS modules: the dispatcher in `__init__.py` gets `gather_image_hook` (the target's own hook, then the filter);
  `material_preview.update_all` (the Update Material Nodes operator) applies the levels nodes; the Use Uniform
  Roughness of the clearcoat branch reads the ORM through them (`output_socket`); the operator's description names the
  levels.
- `tests/test_orm_levels.py` and its row in `tests/README.md`. Expected pixels come from the test's own formula, PNG
  writer and PNG reader (all filter types), not from `orm_levels`.

### Decisions

7. **The fs24 deploy assembles a staging folder first, then copies it into the package.** The export writes into
   `deploy-temp` (also for the cockpit). A staging tree that mirrors the package is assembled there: the model folder
   with the glTF (image URIs pointed at the texture folder) and the bin, the texture folder with every texture the

KTX2 (asked by the maintainer, a finding, not a decision): the SDK describes KTX2 only as the package build's output;
the build modifies pixel data for the shaders, Marketplace builds use their own KTX2, and editing built KTX2 is
strongly discouraged. Supplying KTX2 instead of PNG is not documented. Build time is better saved by giving the build
fewer changed textures (decision 7's copy of differing files only).

different levels would overwrite each other's filtered texture in the shared package folder (the last deploy wins).
