## Session 1: Measurements and Hand-off

- **Date:** 20261103
- **Developer:** uraymeiviar, Claude Opus 5.5

### Objective

MSFS groups instances of one mesh with one material into one draw call (SDK, Modeling Technical Information, Instancing; not for skinned meshes). The glTF exporter writes one mesh per object as soon as the object has any modifier, so objects that share a mesh and all have Weighted Normal do not batch, although they evaluate to the same result.

### Decisions (maintainer)

1. **The exporter fix comes first,** before a tool that detects meshes that could share. Many lost Alt+D copies have Weighted Normal and would not batch until the exporter keeps them as one mesh.
2. **The hand-off runs at once with a sub-agent.**

### Proposals (not answered by the maintainer)

- **P1: throwaway objects only.** The fix runs for multi-exporter duplicates and background exports, the same rule as `gltf_exporter_patches.assign_linked_materials`. An interactive plain export keeps today's behaviour, so nothing in the artist's scene is changed and no restore can be missed when an export raises (`post_export_hook` is not called then). The hand-off follows this proposal until the maintainer says otherwise.
- **P2: Weighted Normal and Auto Smooth only.** Any other modifier leaves the object as it is today. Mirror, Array and the others stay out of scope.

### Measurements (E2 cockpit copy, read-only, no export)

- 2,592 mesh objects, 1,223 mesh data blocks, 664,424 stored vertices; 885 objects sit in merge groups and 1,588 visible mesh objects outside them were measured.
- Outside merge groups, 25 shared meshes have users with modifiers other than Auto Smooth, all Weighted Normal: 209 users evaluate to 29 distinct results. The differences found are normals (14 comparisons) and materials (1). Example: `Circle.008` has 14 users and 2 results; all 34 users of `PedestalMesh.016` are identical.
- **Estimate, not an MSFS measurement** (SDK rule applied to objects outside merge groups, invisible colliders left out): 781 draw calls today, 601 when identical Weighted Normal users stay one mesh. Stored vertices: 254,501 today, 229,146 after. An earlier measurement says the limit of about 500 draw calls was never reached (LOD journal), which does not fit 781, so the estimate is not calibrated.
- **Method:** for each object outside merge groups, evaluate it and compare vertex order, positions (tolerance 1e-5), corner normals (1e-3), UVs (1e-4) and per-face materials from its slots. Draw calls count one per (mesh identity, material).

### Findings in the Code

- `multi_export.py` duplicates with `bpy.ops.object.duplicate(linked=False)`. The cockpit docs report instances surviving this path, so duplicates of one mesh appear to keep sharing a copy. Not checked in this session; step 1 of the hand-off checks it.
- `__gather_mesh` in Blender's `io_scene_gltf2/blender/exp/nodes.py`: `gltf_apply` with `len(modifiers) == 0` uses the mesh data, which instances; any modifier, even disabled, goes through evaluation and gives a copy.
- Hooks run in the order the add-ons are enabled. `fss_enable_addons.py` enables the exporter before `fss_blender_tools`, so the exporter's `pre_export_hook` runs before `lod_model.cull_export` and the merge. An artist's own Blender may enable them in another order.
- `lod_model.drop_small_pieces` shares a trimmed mesh only for objects without modifiers (`not obj.modifiers`). With the fix running first, baked users take this path, so instancing should survive in the trimmed LODs.
- `drop_small_pieces` also shows the idiom for a new mesh: `new_from_object(evaluated)`, then the materials from the evaluated slots with `.original`.

### What Changed

- `instancing.py`: `instance_throwaways(objects, export_settings)` next to `prepare`, with the conditions of step 2 (P1 and P2) and the comparison of the Method. It evaluates with `to_mesh()` to compare and makes the new mesh with `new_from_object(preserve_all_data_layers=True)`, as the exporter's own evaluation does. Users skinned through `find_armature()` count as skinned, also without an Armature modifier. A group of users without any modifier stays on the source mesh. Object-linked slots of baked users become data-linked, so an unused slot that differs does not split the glTF mesh.
- `__init__.py` (dispatcher): `pre_export_hook` calls the rule after `prepare` and before `assign_linked_materials`, with the same list of throwaway objects. A new `gather_mesh_hook` forwards to the simulator's hook, then writes the source mesh name. Without it a plain export (MSFS 2020, plain MSFS 2024) would write `Shared.001`, because the source mesh still holds the name.
- `tests/test_instancing.py`, the docs of step 6, and the prefix WNI in `docs/spec/README.md`.

### Found, Not Changed

**Crash on a plain export after a multi-export and a file load.** `gltf_hooks.Export.msfs_export_settings` is a class attribute the multi-exporter sets; after `read_homefile` it points into a freed scene, and the next plain export reads it in `_hooks_enabled`. This crashed `test_anisotropic_preview` in 1 of 4 runs with the change and 0 of 2 at the previous commit. A small script with the previous commit's code, no rule in it, crashes in 6 of 6 runs in the same line, so the rule is not needed for it. By reading, the deploy drivers do not reach it: fs24 sets the attribute before each export and fs20 never sets it. `tests/test_instancing.py` clears the attribute in its scene set-up. A fix would touch Asobo's `gltf_hooks.py` or the dispatcher and needs a decision.
