### Problem Statement

The MSFS 2024 port (exporter conversion journal) fixed the Blender-to-glTF path, but the work showed that most remaining in-sim defects are not exporter bugs. They are contract drift between the `.blend` and the MSFS project:

1. Behavior XML, `.cfg` light definitions and attachments refer to nodes by name. Blender's duplicate-name suffixes (`.001`, `.002`) end up in the glTF node names, so the reference silently misses (light meshes not visible, frozen switches).
2. The artist cannot see from inside Blender which nodes the project depends on, which animations it plays, or what a sub-model or attachment looks like in place.
3. Interactive helper geometry (clickspots, collision meshes) is made by hand.
4. Performance decisions (merging, materials, LODs) are made blind; the E2 cockpit analysis had to be done with a one-off script.

The E2 project makes this urgent: an E2 cockpit authored in a new `.blend` must drive the existing E1 behavior XML and WASM logic, so it has to satisfy a node and animation contract it did not create.

The exporter add-on (`io_scene_gltf2_msfs_fss`) stays an exporter: it tracks Asobo upstream and must stay mergeable. These features belong in a separate add-on, called **fss-blender-tools** here. It lives in its own repository; its production branch is copied into `tools/blender`, like the exporter, and its commit is recorded in `tools/blender/FSS-ADDONS-VERSION.txt`.

### Shared Foundation: the Project Contract

Items 2, 3, 6 and part of 1, 4, 5 and 7 need the same input: what the MSFS project expects from a given glTF (node names, animation names and lengths, attachment anchors, LOD `minSize` values, clickspot components). `project-tree.exe` already computes most of it (validator journal, Session 7: LOD 0 node pools across `<MergeModel>`, template macro expansion, `<AttachToNode>` anchors).

The add-on should ask project-tree rather than parse the project itself; a Python re-implementation of XML crawling and template expansion would be a second implementation that disagrees with the first. Two ways to ask:

- **One-shot query:** Blender runs `project-tree.exe --query ... --json` and reads the reply. Simple and stateless, but every call indexes the project again.
- **Resident server (direction to evaluate):** Blender starts project-tree once per session; it indexes the project once and answers JSON-RPC requests over stdin/stdout ("which nodes does LOD 0 of `E195_INTERIOR.xml` expect", "where is `SW_ELEC_APU_GEN_KNOB` referenced"). MCP is JSON-RPC over stdio as well, so the same server could serve Blender and AI agents. Blender polls replies from a timer, so its UI never blocks.

The project-tree indexing time has not been measured, so whether the one-shot query is fast enough is unknown. The request and reply format is a shared contract and is specified in the validator journal, not here.

### Wish-List Items

#### 1. Sub-model merging and attachment preview

- **Why / what for:** an aircraft is assembled at runtime from `<MergeModel>` glTFs (wings, engines) and `<ModelAttachment>` models (ground equipment, E2 parts reused from E1). In Blender the artist sees only one piece. A preview avoids modelling against guesses, and shows whether an attachment anchor sits where the part is expected.
- **Feasibility: high.** Import the referenced glTF with the Khronos importer (or link the source `.blend` if known) into a preview collection. Parent it to the anchor object named by `<AttachToNode>`, or place it at the merged-model origin. Mark the collection as preview, so that it is excluded from every export preset and never saved as authored data (or saved but locked).
- **Blockers / open points:** resolving which glTF and which anchor needs the project contract. Imported Asobo materials preview only approximately; that is acceptable for placement. Must be certain that a preview collection can never leak into an export (the multi-exporter selects by collection).

#### 2. Batch rename of duplicate-suffix names, checked against the project

- **Why / what for:** Blender enforces unique object names, so a copied `LIGHT_NAV_L` becomes `LIGHT_NAV_L.001`. The glTF node gets that name, and the `.cfg` or XML that refers to `LIGHT_NAV_L` misses it silently. The freighter cabin GLTFValidator duplicate-name error came from the same family of problems.
- **Feasibility: high.** Scan objects (and materials, actions) for `.NNN` suffixes. With the project contract, classify each: the base name is expected by the project (rename it), the base name is unused (cosmetic), or two objects would collide after stripping (report; rename neither).
- **Decision:** the fix renames the Blender objects themselves; there is no export-time name alias.
- **Blockers / open points:** the contract for the cross-check. Renaming must not break Blender-side references (drivers, constraints, NLA targets reference objects by pointer, so they survive; Python scripts and text references by name would not).

#### 3. Missing nodes and animations expected by the project

- **Why / what for:** the reverse view of item 2. Before export, list what the project expects but the `.blend` lacks: nodes, animation clips (`ANIM_NAME`, `#NODE_ID#` default), clip length (`ANIM_LENGTH`), and suspected wraps (`ANIM_WRAP`). Today these are found in the sim as a knob that does not move.
- **Feasibility: high**, given the contract. Blender-side facts are easy to read: object names, actions and NLA strips per object, and frame ranges. Matching rules follow the validator journal's animation defect classes, applied at the source instead of on the exported glTF.
- **Blockers / open points:** the export names an action as the glTF animation name differently per exporter setting (NLA track vs action name, possible `Armature|` prefixes). The rule for what name the exported clip will get must be taken from the exporter code, not assumed. Template-generated names that stay unresolved are reported as unknown, not as missing.

#### 4. Clickspot and collision mesh generator

- **Why / what for:** small knobs and switches need a larger, simple invisible mesh to be clickable, and doors or panels need collision. These are made by hand today, inconsistently named and sometimes heavier than the visible part.
- **Feasibility: high.** From selected objects, generate a box, convex hull (`bmesh.ops.convex_hull`) or inflated copy. Assign the Invisible material, name it by convention, parent it to the source, and keep it in the source's export collection. The same tool can build the cockpit collision mesh around the instruments, which the SDK calls mandatory for mouse depth and VR (`cockpit-collision-meshes-and-occluders.md`, `vr-helpers.md`).
- **Representation:** mouse interaction uses meshes with the Invisible material (`covers-chocks-and-pins.md`; skinned meshes never react to interactions, so they always need one). This is the current FSS practice. The Asobo collision gizmos (box, sphere and cylinder objects exported as `ASOBO_gizmo_object`) are physical colliders recommended for scenery, and only static objects collide with the user aircraft, so they are not used for clickspots.
- **Blockers / open points:** the naming convention for clickspot meshes must match what the behavior templates expect (node vs mouse-rect node), which is again the contract.

#### 5. FSS node metadata

- **Why / what for:** some objects have a role the `.blend` cannot express today: clickspot, audio emitter position, MSFS light node, emissive mesh, WASM-rendered display screen, debug mesh (visible in-sim only under a debug condition). Tagging them makes the role explicit, and the other tools act on it (item 4 generates for clickspots, item 6 groups by role, item 7 accounts for emissive and display materials, export can strip debug meshes from release).
- **Feasibility: high.** A `PropertyGroup` on `bpy.types.Object` (role enum plus role-specific fields: light type, sound name, display texture name), stored in the `.blend`, with a panel and a role-coloured overlay. Optionally written to glTF `extras` if the exporter's custom-property option is used; MSFS ignores `extras` (to verify).
- **Bake settings:** the same metadata carries per-object bake settings for item 18: bake role (target, occluder only, hidden), AO mode (unique on the second UV map, or generic in the shared texture), sheet group, resolution, float distance along the motion axis, and the flood circuits that light the object. Defaults are inferred from what the object already is (material type, instanced or not, normalized input, item 5 role), and collections pass their settings to their objects, so artists only mark exceptions. The panel shows each object's effective setting and where it came from (default, collection or object). Stored in the `.blend`, never exported.
- **Functional roles replace the functional collections:** roles (clickspot, screen, collider, light mesh, decal, reference) are stored as plain custom properties, readable and editable in vanilla Blender, and mostly inferred (Invisible material, Decal type, Collision tag, materials named in `panel.cfg`), so only exceptions are tagged. A panel and overlay list and filter them; a one-time operator converts the current functional collections (`CLICKSPOTS`, `SCREENS`, `COLLIDERS`, `LIGHT_MESHES`, `DECALS`, `REFERENCES`) into roles. `REFERENCES` becomes a do-not-export role. Picked up as generic tags (no inference, no MSFS roles): [20261014.fss-blender-tools-tags-and-merge.md](20261014.fss-blender-tools-tags-and-merge.md).
- **Blockers / open points:** what each role means in the project must be defined first. A WASM display has to match a `panel.cfg` `[VCockpit]` texture name and a material. A light node has to match a `systems.cfg`/`lights` entry. A debug mesh is shown by a visibility behavior and must render on top of every other mesh. No aircraft material in the SDK or the exporter disables the depth test: `NoZTest` exists only for scenery objects, `IgnoreZTest` only for the mouse-rect highlight, and Draw Order only sorts decal, glass and windshield materials. Candidates (Ghost material, emissive glass) need a sim test; until then "always on top" is a blocker. Some of these could be checked by project-tree once the metadata is exported.

#### 6. MSFS project view

- **Why / what for:** a cockpit `.blend` has thousands of objects, and most are static. The artist needs a tree that shows only the objects the project refers to (by component, template, attachment, light, display), with their status, and can select them. Optionally play the animation that a component's template uses.
- **Feasibility: high for the view, medium for playback.** A custom `UIList` panel built from the contract plus the item 5 metadata. Clicking selects and frames the object; a filter hides or isolates everything else (local view or temporary hide). Playback: solo the matching action or NLA strip and scrub its frame range. Mapping the template's input (an RPN expression of L:Vars) to a frame is out of reach without an RPN evaluator, so playback is a plain 0..`ANIM_LENGTH` slider.
- **Blockers / open points:** the contract. Changing NLA solo or mute state for playback must be restored exactly, like the exporter's tweak-mode handling.

#### 7. Draw-call, batch and active-LOD prediction

- **Why / what for:** the E2 cockpit analysis estimated draw calls at one per rendered material per object, and what merging static parts per material and zone would save. A live panel would let the artist see the effect of a merge or material change before exporting and testing in the sim.
- **Scope:** an approximate figure for comparing layouts, not an accurate prediction. Two numbers bracket it:
  - **Unbatched:** sum over objects of rendered materials. One object with several materials needs several draw calls.
  - **Batched:** distinct (mesh, material) pairs, counting linked copies of the same non-skinned mesh with the same material as one call (SDK (FSS aircraft repository `doc/msfs-sdk/pages/models-and-textures/modeling-technical-information.md`), Performance Metrics). Different meshes sharing a material are not documented as batched.
  Invisible and collision materials are excluded. Both are shown per export preset and LOD, split into static and animated.
- **Feasibility: high** for the counts (the E2 analysis script already computes them). **Medium** for active LOD: MSFS selects a LOD by the model's screen size against each `<LOD minSize>`, so the view camera's distance and FOV give a predicted LOD. It needs the `minSize` values from the model XML (contract) or the LOD tools add-on.
- **Blockers / open points:** the exact `minSize` screen-size formula has to be confirmed in the SDK docs. The SimObject Statistics Profiler exists only in the sim's DevMode and cannot be read from Blender; comparing against it is an optional manual check, not part of the tool.

### Suggested Additional Items

8. **Export-time merge by `MERGE_` groups.** An EMPTY named `MERGE_<name>` marks a merge group; its children in the parent hierarchy are the members, so adding an object is just parenting it. In the export copy only, the static member meshes are joined into one mesh that takes the EMPTY's place, named `<name>` without the prefix. The walk stops (that subtree exports unmerged) at animated or skinned objects, objects the project refers to, roles that must stay separate (clickspot, collider, screen, light mesh, glass) and nested `MERGE_` groups, which merge on their own. XML-referenced EMPTYs therefore stay as they are; put them under the `MERGE_` EMPTY instead of renaming them. Decals merge only with decals, per material and Draw Order. A report before export lists each group (objects in, meshes out, materials, objects kept separate and why). The `.blend` is never changed. Implemented in fss-blender-tools, plugged into the exporter's pre- and post-export hook (maintainer decision). Interim manual alternative: a Geometry Nodes join (Collection Info, Realize Instances, Join Geometry) on the panel. Picked up: [20261014.fss-blender-tools-tags-and-merge.md](20261014.fss-blender-tools-tags-and-merge.md).
9. **Instancing candidates and blockers.** Find meshes with identical geometry that are not linked (hash of vertex and face data), and offer to link them. Also report shared meshes whose users will not be instanced: the glTF exporter gives every object that has any modifier its own mesh copy (only Auto Smooth alone with the same angle is rescued by `instancing.py`), so a shared mesh with a modifier on each user is exported once per user. Sorted by wasted copies, with the reason (for example `C3_001`: 178 users, Weighted Normal on each, exported 178 times in the E195 cockpit). A "bake shared modifiers" operator applies an identical, mesh-only modifier stack (Weighted Normal, Auto Smooth, Triangulate, Edge Split) once onto the shared mesh data and removes it from the users, so they are instanced; it refuses when the stacks differ, a modifier depends on per-object data (target objects, differing vertex groups, armatures) or the users carry different materials. Runs after the report, with undo.
10. **Material consolidation.** Find duplicate materials (`.001` copies, identical textures and parameters) and objects split only by such duplicates. Each duplicate is a draw call.
11. **Texture and path check.** Missing images, absolute paths and paths outside the project (the magenta `G:\Cockpit.blend` case), and textures with no `.png.xml` in the target texture folder (shared with the validator).
12. **Exported glTF diff.** Compare a new export against the deployed glTF: nodes, animations, materials and primitive counts added or removed. This would have caught several regressions from the exporter conversion before a sim test.
13. **E1-to-E2 name mapping.** A mapping table from E2 Blender names to the E1 contract names, applied as a batch rename of the objects (item 2). This lets the E2 cockpit drive the E1 behavior XML without hand-renaming.
14. **Export-time decal merge.** Merge static decals per zone, decal material and Draw Order in the export copy; skip decals parented to inputs. Part of item 8, with decal-specific grouping.
15. **Legend bake helper.** For a button with a decal plane on its cap, bake the decal's text into the button sheet (albedo and emissive mask) at the cap's UVs, assign the brightness-circuit material, and remove the plane. Blender's texture baking can project the plane onto the cap. Blocker: the target sheet layout and per-cap resolution must be planned first; the helper fills it, it does not design it.
16. **Decal text generator (glyph-atlas labels).** The user types a label in a panel (text, height, alignment, brightness circuit) and the tool generates one quad per character at the 3D cursor or on the selected surface, UV-mapped to the matching glyph on a shared glyph sheet using the font's metrics. A batch mode builds many labels from a label spec (anchor, text, height, alignment, circuit), written by hand or by an AI agent from panel references through MCP; the operator itself is deterministic. Generated labels merge per zone and circuit, and are not used below LOD0. The same sheet is the source for the legend bake (item 15). Blockers: a font licensed for embedding; glyph padding and quad spacing must avoid mip bleed and BLEND overlap.
17. **Input normalizer and adaptor-empty collapse.** (a) Report inputs whose local axis is off their motion axis or whose origin is far from their pivot. (b) Re-pivot them: symmetry axis for knobs, panel normal for buttons, a spec hint for toggles and levers; shared meshes are made single-user first and identical results relinked as instances. (c) Collapse adaptor empties: the mesh takes the empty's exact transform, inherits its NLA tracks (actions stay valid unchanged) and children, and the empty is removed. Keeps every node name the project refers to; when both the empty and the mesh are referenced, or the empty is a real hierarchy, attachment anchor or light node, it stays and is reported. Depends on the project contract for (c). Rules: Normalizing Inputs (FSS aircraft repository `doc/msfs-authoring/modeling.md`).
18. **Cockpit bake operator.** One call bakes AO and sky light for all of LOD0: classifies targets, occluders and hidden kinds (collisions, clickspots, helpers, decals); creates a second UV map where missing; floats normalized inputs along their motion axis; bakes one 16-bit image per material group with a neutral grey override and white environment; writes to the ORM red channel or Occlusion (UV2) and assigns it; restores the scene. Runs as a background Blender job and re-bakes only groups whose geometry changed. Per-project rules: resolution per sheet, unique or generic AO for repeated parts (default: instanced parts generic). A second mode bakes each flood-light circuit (glareshield, dome) into an emissive mask, enabled after a sim test confirms the look. Reads the item 5 bake settings, so artists set only exceptions. Rules: Baking (FSS aircraft repository `doc/msfs-authoring/baking.md`). Uses item 17 for floating inputs.
19. **Dirt, grime and ice shell generator.** From an airframe part's LOD2, generate offset shells for each dirt type and ice: one for LODs 0 to 2, simplified ones for LODs 4 and 5 and for LOD6, each in its LOD's parent collection, split per modular part, with the SDK's shared textures assigned and vertex alpha for ice. Keeps vertex counts within the LOD budgets. Rules: Airframe Details (FSS aircraft repository `doc/msfs-authoring/airframe.md`).
20. **Sky portal placer.** Place one Sky Portal per window glass object that shows the interior: inner circle inside the window, direction inward, outer angle 180, in the part's LOD0 sub-collection. Checks existing portals for the same rules. Rules: Airframe Details (FSS aircraft repository `doc/msfs-authoring/airframe.md`).
21. **Cockpit LOD1 from window visibility.** Cast rays from exterior viewpoints through the windshield and side windows, and list the cockpit objects that can be seen at all; those form cockpit LOD x1, the rest is dropped from it. Rules: LODs (FSS aircraft repository `doc/msfs-authoring/lods.md`).
22. **Transparency sorting-risk check.** From the pilot eye points, find transparent objects (glass, windshield, decal) that overlap on screen with bounding-box centres close enough to swap order as the head moves; suggest a split or Draw Order values. Rules: Materials (FSS aircraft repository `doc/msfs-authoring/materials.md`).
23. **Silhouette check across LODs.** Render silhouette masks of LOD0 and each lower LOD at its switch distance from several angles; flag LODs whose outline or high-contrast details differ visibly.
24. **Registration mesh check.** Fuselage registration meshes horizontal in flight attitude, in their own collection, UVs using the whole texture.
25. **Exterior light audit.** Every light node has its emissive mesh; emissive maps named `_emis`; brightness consistent with the MSFS 2024 photometric values.
26. **Wing-flex joint helper.** Create and check the WingFlex helper nodes and their naming; the joint count and names must first be confirmed in the SDK (Wingflex (FSS aircraft repository `doc/msfs-sdk/pages/models-and-textures/modeling/aircraft/airframe/animations/wingflex.md`)) and against the XML checks in project-tree.
27. **Automated LOD generator.** Generate all LODs from LOD0: an AI agent directs a deterministic pipeline (part classification, per-part parameters, iteration on flagged parts), the geometry comes from a fork of flow-lod with Blender Decimate and meshoptimizer plus an MSFS layer (hierarchies, node names and NLA tracks kept, small-feature removal at `minSize`, SDK budgets, merge and atlas, proxy at LOD5 and 6), and quality is measured by render comparison at each LOD's switch size. Research, existing tools and evaluation plan: [20261010.automated-lod-generation.md](20261010.automated-lod-generation.md). Uses items 19 and 21.
28. **Stupidity check.** One report, each finding with severity, the object and a fix. Geometry: duplicate vertices, duplicate and zero-area faces, loose geometry. Hierarchy: exported objects under a parent that will not export; the glTF exporter re-attaches the child to the nearest exported ancestor and the parent's animation is lost, so the highest severity goes to hidden parents that are animated or referenced by the project. Transforms: non-uniform scale under rotated children (shear glTF cannot store), negative and unapplied scale, objects in several collections, more than two UV maps, objects far from the origin. Bloat: packed images, fake-user data, data used only by non-exported objects, extra UV maps and colour attributes, unused slots and vertex groups, with sizes, purged after a dry run. External add-on data: traces of add-ons outside the bundled `tools/blender` set (custom properties, linked libraries with absolute paths, undefined node types, drivers calling add-on functions, registered text blocks); because a missing trace fails silently on another PC, a warning is shown when such a file is opened or saved, and a clean-external-add-on-data operator removes or localizes them with a backup. Runs items 2 and 11 in the same report. Fixes run only after the report. First rule implemented: Fix Broken Bone Parents (an object with a parent bone on a parent that is not an armature), see [20261014.fss-blender-tools-tags-and-merge.md](20261014.fss-blender-tools-tags-and-merge.md) Session 6. Rules: Blender and the FSS Exporter (FSS aircraft repository `doc/msfs-authoring/blender-export.md`).

Deferred: tools for passive (AI traffic) aircraft, including parallax window setup, until a passive E-Jet is planned.
